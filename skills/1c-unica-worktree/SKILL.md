# Unica и ворктри: привязка воркспейса, cwd, второй экземпляр

Итог живых проб в ворктри (2026-10-08/09, unica 0.13.0-rc.7). Инициализация
самого воркспейса — инвариант 5 скилла `1c-contour`
(`.zcode/1c/scripts/init_worktree.sh`); здесь — как юника находит дерево.

## Как Unica привязывается к воркспейсу (0.13)

- Привязка происходит **один раз при старте MCP-сервера** и не следует за
  сессией: экземпляр, поднятый от основного дерева, в ворктри не
  «переезжает». Один экземпляр = одно дерево.
- Каналы выбора воркспейса по убыванию приоритета
  (`workspace_context.rs`, unica 0.13.0-rc.7):
  1. per-call метаданные хоста (codex-sandbox);
  2. первый MCP `roots` от клиента;
  3. env проекта (`CLAUDE_PROJECT_DIR`, `ZCODE_PROJECT_DIR`);
  4. cwd запуска (канал `LaunchCwd`) — только standalone-режим.
- **Строгий режим**: запуск через `launch.sh`/`unica-bootstrap` ставит
  `UNICA_HOST_CONTEXT_REQUIRED=1` и `UNICA_RUNTIME_MANIFEST` — cwd-фолбэк
  запрещён (fail-closed, отсутствие контекста = ошибка). Сервер хоста в
  контуре живёт именно в строгом режиме.
- **Аргумент `cwd` вызова воркспейс не переключает**: гейты смотрят на cwd
  вызова, юника — на привязку экземпляра. Рассинхрон = гейт видит ворктри,
  а правится основное дерево.
- Диагностика привязки: `unica.view {}` → `structuredContent`:
  `workspaceRoot`, `workspaceRootOrigin` (канал и переменная, напр.
  `startupEnvironment/CLAUDE_PROJECT_DIR`), `effectiveSourceRoot`.

## Заведение юники в ворктри

1. **Интерактивно (канон)**: перезапустить сессию ZCode с открытием в
   ворктри — хост сам привяжет сервер к новому корню. Сюда же ведёт
   подсказка хука `worktree_hint` после `git worktree add`.
2. **Автономно (скрипт, CI, субагент)**: второй экземпляр через тот же
   `launch.sh` кэша плагина, которым хост поднимает сервер, с env на
   нужное дерево; cwd процесса — ворктри:

   ```bash
   CLAUDE_PROJECT_DIR=<ворктри> \
   UNICA_HOST_CONTEXT_REQUIRED=1 \
   UNICA_RUNTIME_CACHE_DIR=~/.zcode/cli/plugins/data/unica@*/runtimes \
   CLAUDE_PLUGIN_ROOT=<кэш плагина unica> \
     bootstrap/launch.sh   # stdio; handshake — как в scripts/unica_ping.py
   ```

3. **Проверка привязки**: `unica.view {}` — `workspaceRoot` = ворктри;
   `unica.resolve main:Configuration` — файл внутри ворктри; `unica.check
   {}` — готовность (копия ИБ + `build/hash-storages/` с основного дерева
   даёт `ready`, пустая база из `--empty-ib` требует первой сборки).

## «The host did not supply workspace context» — диагноз

Ошибка строгого режима без хост-контекста: обёртка включила
`UNICA_HOST_CONTEXT_REQUIRED=1`, а env/roots не подала. Это **не** удаление
cwd-механики в 0.13 (такой вывод уже стоил ложной эскалации в ворктри-ране).
Лечение: подать `CLAUDE_PROJECT_DIR=<дерево>` или убрать строгие переменные
(см. ниже), но не искать выключенную фичу.

## Прямой запуск (cwd-канал) — запасной ход

Бинарь рантайма (`…/runtimes/unica/<версия>/linux-x64/bin/linux-x64/unica`)
без `UNICA_HOST_CONTEXT_REQUIRED` и `UNICA_RUNTIME_MANIFEST` работает
standalone: воркспейс = cwd запуска. Для хостов, чьей обёрткой запуска не
управляешь. В ZCode-контуре предпочитай рестарт сессии или второй
экземпляр: привязка через env видна в `workspaceRootOrigin` и не зависит от
cwd вызывающего.

## cwd-механика контура

- Хуки в `.zcode/config.json` разводятся **относительными путями**
  (`.zcode/hooks/…`, так работает `wire_config.py`): работают из корня
  любого дерева (в ворктри свой checkout), но ломаются, если cwd сессии
  остался в подкаталоге — гейты Bash/Write/Edit падают до исполнения,
  `cd` обратно той же командой не проходит (хук вызывается раньше).
- Правило: cwd сессии = корень дерева (основного или ворктри), команды —
  с абсолютными путями; пересадка cwd «на постоянку» = рестарт сессии.
- Юнику `cd` не переключает в любом направлении: привязка при старте.
- Экстренное разблокирование без рестарта: субагент (стартует из корня —
  его хуки живы) кладёт в застрявший каталог шимы-делегаторы (`os.execv`
  на настоящий хук), одна команда `cd` возвращает cwd, шимы удаляются.
  Сами хуки проекта при этом не править. Автономный ран (оператора спросить
  некого) вправе применить рецепт без согласия при всех трёх условиях:
  шимы живут ровно одну команду `cd` и удаляются сразу, хуки не правятся,
  в финальном отчёте — отдельная строка об отклонении. Правка самих хуков
  и отключение гейтов — только с согласия оператора, автонома это не
  касается.

## Грабли живых проб

- `unica.view` отдаёт данные в `structuredContent`; `content` бывает
  пустым — скрипты парсят `structuredContent`.
- `unica.docs` уходит в async и ищет от привязанного воркспейса (может
  попасть в platform-help чужого дерева) — факт привязки проверяют
  `unica.view`, не docs.
- `repositoryReady: false` на репо с >65536 записей
  (`git.inspection_incomplete`) — свойство большого репозитория, не дефект
  запуска.
- Серверная база одна на все деревья — операции разводит замок (инвариант 4
  скилла `1c-contour`); файловая база в ворктри своя (относительный `File=`).
- Зачистка: чужие процессы `unica-bootstrap` (другие проекты и сессии)
  опознаются по `/proc/<pid>/environ` и `readlink /proc/<pid>/cwd`; артефакты
  в `/tmp` (`1c-db-<hash>.log`, `1c-mcp-proxy-<hash>.log`) именуются
  sha1-префиксом пути дерева.
