# Контур 1С под ZCode: инварианты и маршрутизация

## Инварианты (исполняются гейтами)

1. **Исходники 1С правятся только через Unica MCP** (`mcp__unica__*`).
   Прямая правка `Write`/`Edit`/`sed -i`/перенаправлениями блокируется гейтом
   `unica-source-gate`. Чтение (`Read`, grep, glob) — свободно.
   Разовая прямая правка, которую Unica не выражает (например, комментарий
   вне тела метода), — через `.zcode/unica-gate-escalations.txt` в корне
   дерева: одна строка = путь относительно корня; после правки строку убрать.
2. **Расширение грузится всегда полной пересборкой** (`fullRebuild: true`),
   **основная конфигурация — никогда**: частичная загрузка расширений падает
   на формах, полная пересборка main — десятки минут. Гейт блокирует
   нарушение обоих инвариантов.
3. **Мутация — только после сверки с документацией** (гейт `docs-before-design`):
   перед `code.patch`/`meta.*`/build/load в сессии должен быть непустой вызов
   `unica.documentation.search/get` или `unica.standards.search/explain`.
   Пустой результат не считается. Мутация метаданных сбрасывает флаг: новое
   структурное решение — новая сверка. Исходники говорят «как сделано»,
   документация — «что допустимо платформой».
4. **Серверная база одна на все деревья**: одновременные тяжёлые операции
   разводит файловый замок (TTL 20 мин); занятость увидишь блоком от гейта.
5. **Ворктри инициализируется скриптом** `.zcode/1c/scripts/init_worktree.sh`
   (`v8project.local.yaml`, `build/tools/`, база) — unica-вызов из
   неинициализированного ворктри блокируется.
6. **Третий идентичный повтор упавшей команды заблокирован** — диагностируй
   или меняй условия (гейт `retry-discipline`).
7. **Прод-контур fail-closed**: изменяющие инструменты тест-контура
   (`tc_execute_*` у 1c-testpilot, `execute_code` и др. у 1c-db) без
   признака `test` (ключ `contour:` в `v8project.local.yaml` или
   `.zcode/contour`) блокируются. Разовое разрешение — строка в
   `.zcode/mcp-write-allow.txt`.

## Маршрутизация: файл → инструмент Unica

| Файл / тип | Инструмент |
|---|---|
| `*.bsl` (модуль) | `unica.code.patch` |
| `Form.xml` | `unica.form.edit` / `unica.form.compile` |
| `Configuration.xml` | `unica.cf.edit` |
| XML метаданных (справочник, документ, регистр…) | `unica.meta.edit` / `unica.meta.add` |
| `Role.xml` / `Rights.xml` | `unica.role.edit` / `unica.role.compile` |
| СКД `Template.xml` | `unica.dcs.edit` / `unica.dcs.compile` |
| MXL `Template.xml` | `unica.mxl.compile` / `unica.mxl.decompile` |
| `Subsystem.xml` | `unica.subsystem.edit` / `unica.subsystem.compile` |
| `CommandInterface.xml` | `unica.interface.edit` |
| XDTO `*.xsd` | `unica.xdto.edit` |
| Заимствование в расширение | `unica.cfe.borrow` |
| Перехват метода (CFE) | `unica.cfe.patch_method` |

Все вызовы Unica обязаны нести `cwd` корня проекта (или ворктри).
Мутации — только с `dryRun: false` по явному запросу пользователя.

## Маршрутизация качества кода (приоритет сверху вниз)

| Задача | Куда |
|---|---|
| Форма кода: форматирование, naming, декомпозиция, doc-comments, ветвление, style-review | скилл `1c-bsl-code-style` — **высший приоритет**; машинный чекер гоняет гейт `bsl-style-gate` после правок `.bsl` |
| Вызов подсистем БСП: какой публичный API правильный, сигнатуры, антипаттерны | скилл `bsp` (БСП 3.1.11) + сверка `bsp_api.py --src src/cf`; версия БСП проекта отличается — перепроверка |
| Поиск по стандартам/паттернам в живой конфигурации | `unica:bsp-patterns`, `unica.standards.search` / `explain` |
| Проектирование API своей конфигурации | `unica:api-design` |
| Диагностика кода | `unica.code.diagnostics` — advisory: никогда не блокирует и не диктует форму |
| Синтаксис платформы вне БСП | `unica:platform-help` |

**Правило конфликта**: замечания стандартов (v8std/БСП) и стат-анализа
(АПК:\*, BSLLS:\*, v8cs:\*), противоречащие паку `1c-bsl-code-style`,
не применяются. Правится по паку; стандарт можно цитировать как обоснование.
Форму кода не «улучшай» по диагностике, если пак доволен.

## Тест-контур и данные базы

- E2E-сценарии 1С: скилл `1c-test-contour` (record-first, readback, ЖР-сверка)
  и workflows `1c-e2e-run` / `1c-e2e-record`.
- Данные базы, запросы, метаданные, журнал регистрации: скилл `1c-db-data`
  (MCP `1c-db` = 1c-mcp-toolkit).
- Юнит-тесты, написанные агентом, контуром не поддерживаются: внутренний
  оракул (тот же автор, коррелированные ошибки). Проверка поведения — e2e
  по записанным сценариям + журнал регистрации.

## Эскалации и обходы

| Обход | Файл | Правило |
|---|---|---|
| Прямая правка исходника | `.zcode/unica-gate-escalations.txt` | одна строка = путь; причина комментарием `#`; после правки строку убрать |
| Изменяющий вызов в прод-контуре | `.zcode/mcp-write-allow.txt` | строка = короткое имя инструмента или `*`; каждое разрешение пишется в аудит |
| Сверка не нужна для этой мутации | `.zcode/doc-gate-escalations.txt` | как в unica-гейте |

Все решения гейтов пишутся в `~/.zcode/logs/rule-audit.jsonl`.
Диагностика контура — команда `/1c-doctor`.
