# Контур 1С под ZCode: инварианты и маршрутизация

## Поверхность Unica 0.13: глаголы и режимы

Каталог базовых блоков — https://ingvarconsulting.github.io/unica/scenarios.html ;
источник контракта — словарь `unica.run {}` (вызов без op) и словари узлов
(`view` корня/узла). Имена ниже — карта, не контракт.

| Глагол | Режим | Зачем |
|---|---|---|
| `unica.search` | чтение | найти объект по имени/синониму/виду, найти код/литералы/вызовы |
| `unica.view` | чтение | состав и свойства узла, **словарь операций узла** (что с ним можно) |
| `unica.diff` | чтение | сравнить узлы/версии, доказать обратимость правки |
| `unica.resolve` | чтение | путь из диффа/файл+строки → логический адрес |
| `unica.docs` | чтение | документация: platform-help / development-standard / configuration-documentation |
| `unica.apply` | **план → запись** | ВСЕ правки: свойства, реквизиты, формы, BSL-код, роли, СКД, макеты, подсистемы, XDTO, поддержка поставщика |
| `unica.check` | чтение | валидация узла после правки (валидатор по виду: cf/cfe/form/dcs/mxl/role/…) |
| `unica.run {op, args, dryRun}` | действие | сборка/ИБ: `push` (force, full), `upload`, `apply`, `reset`, `make`, `launch`, `infobase.*`. Аргументы операции — ВЛОЖЕННО в `args` (плоская форма отвергается); `dryRun: true\|false` обязателен явно; платформенные операции — async: ответ = задача, результат через `unica.task.result` (waitMs ≤ 7000) |
| `unica.task.*` | — | durable-задачи: get/result/cancel (долгие вызовы) |

Канон правки (сценарий S159): `search → view → apply (план) → apply (запись) →
view/check/diff (перепроверка)`. План `apply` не меняет байты — пиши через
него, запись — после сверки плана.

## Инварианты (исполняются гейтами)

1. **Исходники 1С правятся только через Unica** (`mcp__unica__*`). Прямая
   правка `Write`/`Edit`/`sed -i`/перенаправления блокируется гейтом
   `unica-source-gate`. Разовая прямая правка, которую поверхность не
   выражает, — через `.zcode/unica-gate-escalations.txt` (одна строка =
   путь; после правки строку убрать).
2. **Мутация — только после сверки с документацией** (гейт
   `docs-before-design`): перед `unica.apply`/`unica.run {op: push|upload|
   apply|reset}` в сессии нужен непустой вызов `unica.docs` (или
   `unica.search`). Пустой ответ не считается. Структурная мутация
   (не-code ops, push/upload) сбрасывает флаг — следующее структурное
   решение снова требует сверки; серия правок кода (`apply` с ops `code.*`)
   флаг не сбрасывает.
3. **Инварианты пересборки — правила ПРОЕКТА, не контура** (0.13: `push
   {force, full}` вместо 0.12-`fullRebuild`, semantics изменилась). Гейт
   применяет `unica.rebuild_rules` из `.zcode/1c/contour.json`; пока правила
   не включены сверкой на живом стенде — гейт нейтрален.
4. **Серверная база одна на все деревья**: тяжёлые операции разводит замок
   (TTL 20 мин). Файловая база изолируется сама: `File=` относительный путь
   от каталога `v8project.yaml` — у каждого ворктри своя.
5. **Ворктри инициализируется** `.zcode/1c/scripts/init_worktree.sh`
   (`v8project.local.yaml`, `build/tools/`, база); unica-вызов из
   неинициализированного ворктри блокируется.
6. **Третий идентичный повтор упавшей команды заблокирован** — диагностируй
   или меняй условия.
7. **Прод-контур fail-closed**: изменяющие инструменты тест-контура
   (`tc_execute_*` у 1c-testpilot, `execute_code` и др. у 1c-db) без
   признака `test` (ключ `contour:` в `v8project.local.yaml` или
   `.zcode/contour`) блокируются. Разовое разрешение — строка в
   `.zcode/mcp-write-allow.txt`.

Все вызовы Unica несут `cwd` корня проекта (или ворктри). Мутации — записью
(не планом) только по явному запросу пользователя.

## v8project.yaml 0.13 — что изменилось (правила 0.12 устарели)

- Ключ `builder` отвергается схемой: исполнитель — per-operation
  `providers` (`designer` / `agent` / `ibcmd`), по умолчанию его выбирает
  раннер (v8-runner 0.11.2). Практика наших проектов: файловая база — ibcmd,
  серверная — дизайнер; переопределяется в `providers`.
- `infobase.connection` → `infobases.origin.connection` (legacy-ключ
  читается на миграции; `v8project.local.yaml` перекрывает, включая
  `providers`).
- Относительные пути (`workPath`, `File=…`, source-set'ы) — от каталога
  основного конфига, т.е. от корня ворктри.
- Веб-публикация — вне поверхности 0.13 (контрактный gap юники; вручную по
  её web-spec). Тест-контуру публикация не нужна: testpilot поднимает
  клиент сам, 1c-mcp-toolkit живёт в сессии 1С.

## Маршрутизация качества кода (приоритет сверху вниз)

| Задача | Куда |
|---|---|
| Форма кода: форматирование, naming, декомпозиция, doc-comments, ветвление, style-review | скилл `1c-bsl-code-style` — **высший приоритет**; машинный чекер гоняет гейт `bsl-style-gate` после правок `.bsl` |
| Вызов подсистем БСП: какой публичный API правильный, сигнатуры, антипаттерны | скилл `bsp` (БСП 3.1.11) + сверка `bsp_api.py --src src/cf`; версия БСП проекта отличается — перепроверка |
| Стандарты разработки | `unica.docs {source: development-standard}` |
| Проектирование API своей конфигурации | скилл `unica:api-design` |
| Диагностика кода | advisory: никогда не блокирует и не диктует форму |
| Синтаксис платформы | `unica.docs {source: platform-help}` / скилл `unica:platform-help` |

**Правило конфликта**: замечания стандартов и стат-анализа, противоречащие
паку `1c-bsl-code-style`, не применяются. Правится по паку; стандарт —
только как обоснование.

## Тест-контур и данные базы

- E2E-сценарии: скилл `1c-test-contour` + workflows `1c-e2e-author` (агент
  сам пишет тест) / `1c-e2e-run` (прогон pytest без модели). Write-first:
  носитель сценария — код в `tests/e2e/`, readback, ЖР-сверка, приёмка-код.
  Человек в цикле прогона не участвует.
- Данные базы, запросы, метаданные, ЖР: скилл `1c-db-data` (MCP `1c-db`).
- Юнит-тесты, написанные агентом, контуром не поддерживаются: внутренний
  оракул. Поведение проверяется e2e по реальным бизнес-потокам + ЖР
  (лог-дривен).

## Эскалации и обходы

| Обход | Файл | Правило |
|---|---|---|
| Прямая правка исходника | `.zcode/unica-gate-escalations.txt` | одна строка = путь; причина комментарием `#`; после правки строку убрать |
| Изменяющий вызов в прод-контуре | `.zcode/mcp-write-allow.txt` | строка = короткое имя инструмента или `*`; пишется в аудит |
| Правила пересборки проекта | `.zcode/1c/contour.json` → `unica.rebuild_rules` | включать только после сверки на стенде |

Все решения гейтов пишутся в `~/.zcode/logs/rule-audit.jsonl`.
**Правка применилась, но ты подозреваешь блокировку (молчаливый ответ
инструмента)?** Рантайм ZCode не доставляет модели сообщения
блокирующего PostToolUse — читай хвост журнала: `tail
~/.zcode/logs/rule-audit.jsonl` (запись `decision: blocked` с rule и
причиной; стайл-нарушения перечислены построчно `путь:строка: [id]`).
Диагностика контура — команда `/1c-doctor`.
