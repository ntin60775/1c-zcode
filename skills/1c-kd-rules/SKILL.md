# Правила обмена через MCP 1c-kd (kd-rules-mcp)

Сервер — вендор-копия [egordoronchenko/kd-rules-mcp](https://github.com/egordoronchenko/kd-rules-mcp)
(MIT, пин и процедура синка — `vendor/kd-rules-mcp/UPSTREAM.md` контура). Транспорт — streamable
HTTP на петлевом интерфейсе; в проекте сервер объявляет `wire_config.py` под именем **`1c-kd`**,
URL берётся из `.zcode/1c/contour.json` → `1c_kd.url` (умолчание `http://127.0.0.1:8060/mcp`).
Что во что конвертировать, решает агент; сервер детерминированный — разбирает выгрузки,
предлагает кандидатов, пишет XML и проверяет. Содержательные каноны работы — скиллы
`kd2-rules-build`, `kd2-exchange-pitfalls`, `kd3-rules`; полный список инструментов с
сигнатурами — `vendor/kd-rules-mcp/docs/tools.md` (в репо контура).

## Установка и старт (один раз на машину)

```bash
scripts/install_kd_rules.sh    # станция ~/.local/share/1c-zcode/kd-rules-mcp, uv sync (первый раз — минуты)
scripts/start_kd_rules.sh      # поднять вручную; --status / --stop / --print-config; лог <станция>/kd-rules.log
```

При старте каждой сессии в проекте с разведённым `1c-kd` хук SessionStart
(`kd_session_start.py`) сам будит спящую станцию фоном — руками поднимать не нужно.
Граница: http-подключение MCP происходит на старте сессии, поэтому в сессии,
которая сама разбудила станцию, инструменты могут появиться только после
перезапуска сессии; `1c-kd` при остановленной станции — мягкая зависимость
(doctor даёт WARN, остальное работает). Станция хуком не гасится — гасится
руками `--stop`, когда работа с правилами закончена. Проверка цепочки в
сессии: `project_list`, затем `structure_load_project` (первая загрузка
большой выгрузки — до пары минут, дальше из кэша).

## Подключение своего проекта к станции (делает агент в проекте)

При первой задаче по правилам обмена в этом проекте:

```bash
python3 .zcode/1c/scripts/kd_register_project.py .
```

Скрипт сам находит XML-выгрузку конфигурации (`src/*/Configuration.xml`, формат Конфигуратора — не EDT) и
расширения (`src/cfe/*/`), вписывает проект в `projects.yaml` и `projects.local.yaml` станции и проверяет
запись её же загрузчиком. После ПЕРВОГО подключения (и при снятии) перезапусти сервер — `start_kd_rules.sh
--stop` и старт: список папок (projects.local.yaml) читается один раз на старте; правки выгрузок
существующего подключения сервер подхватывает на лету (projects.yaml перечитывается на каждый вызов).
Ручные опции: `--id` (ключ проекта), `--dump`/`--extensions` (если авто-поиск промахнулся), `--rules-dir`
(папка живых правил), `--check`, `--unregister`.

После регистрации: `project_list` → `structure_load_project` с ключом проекта. Дозаполнение по потребности
(поля описаны в `projects.example.yaml` станции): `bases` (песочница для `exchange_check`/`bsp_check`),
`writable_extensions`, `exchanges`. Порядок расширений в `extensions` — порядок наложения, сверяй с базой.
Правила: если в проекте есть каталог `kd2-rules/` (компонент навыка 1c-project-layout, git-tracked),
register подхватывает его в `rules_dir` сам — сервер пишет туда `rules_save`/`handlers_export`; нет
каталога — register подскажет завести.

## Возможности v1.9.1 (синк 27.10.2026, было 1.3.0)

- **Живые проверки** `live_status`, `live_rules_dump`/`live_rules_check`/`live_rules_install` (установка
  с откатом; запись — в два шага: предпросмотр, затем применение с хешем), `live_nodes_setup`,
  `live_exchange_run`, `live_registration_check`, `live_base_check`. Доступ к базе — адаптер
  «выполнить код» поверх сервера данных (имя настраивается, по умолчанию `vcexecutecode`), только
  базы роли «песочница». В контуре связка адаптера с 1c-db пока не разведена — живые пробы
  при первой КД-задаче на реальной станции.
- **Справка без установленных скиллов**: `reference_get` (разделы `protocol`, `symptoms`, `phases`,
  `handler_params`) и `reference_search` (полнотекстовый, `skill: "kd2"` сужает). Тексты сервер читает
  из папки скиллов — `start_kd_rules.sh` задаёт `KD2_REFERENCE_DIR` сам.
- **Массовые операции**: `rule_update_many` (выбор списком кодов или фильтром, `mode=preview`,
  `expected_count`, правка атомарная), `pko_create_from_candidates` (ПКО+ПКС по многим парам одним
  вызовом, двухшаговый preview/apply).
- `match_objects` предлагает пары переименованным объектам **по составу реквизитов** (класс
  `auto: false` — применяет такую пару только решение агента).
- `ed_validate` модуля универсального формата: интерфейс менеджера, ранние возвраты, направления
  условий, точные имена правил (регистр и концевые пробелы значимы).
- **Изменения поведения против 1.3.0**: `rule_update` без полей — ошибка; вид `pro` убран из
  `rule_create`/`rule_update`/`rule_delete`; `bsp_check` и `exchange_check run` проверяют совместимость
  правил БСП (продолжить при несовпадении версии — `--accept-version-mismatch`).
- **Папка обмена**: `build_packs.py --dest <папка> --side <имя>=<проект> …` (или `--exchange <id>`
  по профилю) собирает каталог вне проектов со скиллами, серверами и памяткой `KD-EXCHANGE.md`
  обеих сторон — разбор обмена парой баз; канон — «Вторая сторона обмена» в
  `kd2-rules-build`/`kd3-rules`.

## Станция и её файлы

- Станция одна на машину: `~/.local/share/1c-zcode/kd-rules-mcp` (переопределяется `KD_RULES_STATION`).
- `projects.yaml` — описания проектов, общий для команды файл (машинных путей в нём нет).
- `projects.local.yaml` рядом — абсолютные пути проекта на этой машине; **в git не попадает**.
- Сервер пишет только в рабочую папку станции (`workspace/`) и в `rules_dir` проекта с флагом `writable`.

## Обновление

`scripts/install_kd_rules.sh` пересинхронизирует код станции (состояние — projects, workspace,
cache — не трогает), затем `start_kd_rules.sh --stop` и старт заново. Новый апстрим — по
процедуре `UPSTREAM.md` (замена вендор-копии, forbidden-names, тесты, пин).

## Границы канала

- Пакет MCP-серверов comol (vibecoding1c: граф кода, синтакс-чекер, БСП-поиск) в поставку
  **не входит**: код обработчиков агент пишет через unica (`mcp__unica__*`), синтаксис —
  проверка BSL-каналами контура.
- `kd_check`/`bsp_check` (штатная загрузка правил в базу КД/БСП) — опциональные проверки
  Windows-машины с платформой; в контур не ставятся, сервер работает без них.
- `rules_dir`/`writable_extensions` дают серверу запись в проект — подключай осознанно,
  прод-выгрузки держите вне записи.
