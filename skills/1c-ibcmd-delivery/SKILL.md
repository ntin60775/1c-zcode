# Поставка исходников через ibcmd: цикл, заимствования, сверка

Разделение ответственности (решение владельца контура, 2026-10-20): всё про
выгрузку/загрузку исходников и поставку — напрямую `ibcmd`; работа над
конфигурацией (чтение, поиск, правки BSL, документация, операции с ИБ,
запуск) — через unica. Выгрузка не равна авторской правке — гейты доставку
ibcmd не блокируют (ловят перенаправления и `sed -i`, а не аргументы утилит).

Опорный кейс: расширение с формой с ручным динсписком (ManualQuery,
агрегатный запрос, соединения с заимствованными объектами) — полный цикл
import → apply --force → export прошёл без единой правки текста запроса,
только метаданными заимствований.

## Первая гипотеза при отказе загрузки — неполная цепочка заимствований

Валидатор import резолвит расширение **в контексте только расширения**:
Конфигуратор мёржит с основной конфигурацией и «прощает» незаметно, ibcmd —
нет. Поэтому «валидатор ругается» = «расширение неполно», а не «инструмент
сломан»; Конфигуратор — не арбитр полноты, ibcmd-валидатор — единственный
полный. Полнота цепочки заимствований — ответственность того, кто правит
метаданные, а не инструмента поставки.

Любой похожий отказ поставки («Неверный путь к данным: Список.X» и иные
отказы резолва ссылок при import/apply) — первым делом проверка цепочки
заимствований, и только после неё текст запроса, формы или кода. Источники
ссылок — не только динсписок: запросы любых видов, типы реквизитов,
ЗНАЧЕНИЕ(…), соединения с подчинёнными сущностями. Неполнота проявляется
группой ошибок сразу и без указания недостающего звена (все поля формы
разом, включая системные вроде `Ссылка`).

## Цепочка заимствований: пять уровней

Заимствовать по цепочке от всего, что ссылается на метаданные:

1. **Объекты верхнего уровня** из ИЗ и СОЕДИНЕНИЕ — `object.borrow` юники.
2. **Подчинённые сущности**: реквизиты, ТЧ с их реквизитами, измерения и
   ресурсы регистров — поштучно. `object.borrow` берёт только верхний
   уровень («from must name a top-level object»; формы — апстрим unica#937),
   остальное — правка XML источника по документированной эскалации
   (allowlist `.zcode/unica-gate-escalations.txt`, скилл `1c-contour`).
3. **Скалярные свойства дескрипторов**, нужные операциям запроса:
   виртуальная таблица среза строится из `Periodicity`/`WriteMode`
   заимствованного регистра — перенести их в adopted-дескриптор (обычный
   заимствованный каталог так же носит `CodeLength`).
4. **Цели типов каждого реквизита** выборки: валидатор тянет тип до конца —
   незаимствованное звено (перечисление, справочник, документ из типа
   реквизита) валит весь запрос.
5. **Значения перечислений** из ЗНАЧЕНИЕ(…): adopted-значение со своим uuid
   и `ExtendedConfigurationObject` = uuid значения родителя. Заимствованное
   перечисление предопределённых не несёт (канон выгрузки расширения) — без
   выписанного значения ЗНАЧЕНИЕ не резолвится. Точечный путь через
   реквизит-ссылку того же типа резолвится и без значения.

## Adopted-канон XML

Свой uuid; `ObjectBelonging=Adopted`; `ExtendedConfigurationObject` = GUID
родителя из основной конфигурации; для ТЧ — свои `GeneratedType`; Type-блок
из основной конфигурации; `ChildObjects` присутствует даже пустой; записи в
`ChildObjects` корня — в каноническом порядке типов. Родительские
GeneratedTypes заимствованного объекта остаются родительскими. Образец —
любой реквизит, заимствованный Конфигуратором («Добавить контролируемое»):
рукописная вставка делается по нему.

## Локализация недостающего звена — за два прогона

Текст запроса не править — неполнота в метаданных. Пробы на копии исходников
(`config import --out` — базу не трогает):

1. Константный SELECT с реальными ON/WHERE — проверяет цепочки соединений,
   не трогая выборку.
2. По одному реальному полю выборки на прогон (остальные поля константами) —
   N импортов называют сломанные ссылки поштучно.

Обе ступени обязательны: константная проба без реальной выборки «зелёная»,
даже когда сломанное поле прячется в списке выборки (живой урок — бисекция
по кускам запроса показала границу, а сломанный референс нашёлся только
поштучным перебором полей).

Алиас таблицы не должен совпадать с именем метаданных или поля другой
таблицы запроса: коллизия имён даёт тот же отказ (подтверждено на отдельном
опыте, не универсально) — дёшево исключить заранее при написании запроса.

## Цикл поставки

- Первый `config export` в каталог — всегда полный: `--sync` требует
  существующий `ConfigDumpInfo.xml` от полного export; иначе
  «Отсутствует ConfigDumpInfo.xml».
- Загрузка: `config import --extension=<имя> <каталог>`; применение:
  `config apply --extension=<имя> --force` — первая загрузка в копию ИБ без
  памяти раннера только с `--force`.
- `config extension create --name=<имя> --name-prefix=<префикс>` ставит
  `safe-mode=yes` по умолчанию — менять через `config extension update`.
- Состав расширений **файловой** базы через ibcmd не доступен (extensions —
  dbms-only, апстрим unica#1103): platform-сессия unica (`extensions.list`)
  или execute_code; подсистемы основной конфигурации — execute_code
  (Метаданные.Подсистемы).
- Сборка `.cfe` — `config save --extension=<имя> --db <файл>`; `config
  import --out` идёт через ту же валидацию и для сборки не годится.
- `--db-path` только абсолютный: относительный резолвится от каталога данных
  автономного сервера (`~/.1cv8/…/standalone-server/`), не от cwd. Пользователь
  базы обязателен; креды в логи и чат не светить.

## Серверная база: ibcmd идёт в СУБД напрямую

ibcmd работает с информационной базой не через кластер, а прямым подключением
к СУБД: `--dbms=<kind>` плюс `--database-server`, `--database-name`,
`--database-user`, `--database-password` (алиасы `--db-server`, `--db-name`,
`--db-user`, `--db-pwd`). Кластер и сеансы 1С в этом режиме не участвуют.

Ограничение платформы, а не политики: **MSSQLServer не поддерживается на Linux
и macOS** — ни источником, ни приёмником. Справка 8.3.27.1859 повторяет это
дважды (у `--dbms` и у `--target-dbms` команды `replicate`): «Внимание: для
операционных систем семейства Linux и MacOS данный тип СУБД не
поддерживается». PostgreSQL, IBMDB2 и Oracle на Linux работают. Отсюда
рабочее правило: серверная база на MSSQL — операции ibcmd только с
Windows-машины; на PostgreSQL — с Linux.

Проверка связи без изменений — `config generation-id` с теми же координатами
(read-only): отвечает номером поколения конфигурации, значит доступ и версия
сходятся.

Режимы и операции (справка `ibcmd help <режим>`): `infobase`
create/dump/restore/clear/replicate; `config`
load/save/check/apply/reset/import/export/generation-id; `extension`
create/update/delete; `server`; `eventlog`. `infobase dump`/`restore` — это .dt,
`config load`/`save` — .cf, `config import`/`export` — XML-исходники.
`config export` умеет `info`, `status` (дифф от `ConfigDumpInfo`) и `objects`
(точечная выгрузка с `--recursive`, `--threads`).

## Свежая база: три пути наполнения

- **Из .dt**: `infobase create --dbms=<kind> --database-server=… --database-name=…
  --database-user=… --database-password=… --create-database --restore=<файл.dt>
  [--force]`; файловая — без `--dbms`, с `--data=<каталог>`.
- **Из XML-исходников git**: `infobase create --import=<каталог src/cf> --apply`,
  расширения — `config import --extension=<имя> <каталог>` плюс `apply`;
  данных нет, только структура — годится для песочницы и проверки цепочки.
- **Между СУБД**: `infobase replicate` (ниже) — единственный способ перенести
  данные без .dt и без промежуточной выгрузки.

`--create-database` требует права CREATEDB у пользователя СУБД, а инициализация
базы 1С — ещё и SUPERUSER: без него создание падает `permission denied for
language c` (ibcmd ставит C-функции, язык c в PostgreSQL недоверенный).
Файловую базу это не касается.

## Миграция между СУБД: `infobase replicate`

Справка 8.3.27.1859: копирует информационную базу в целевую СУБД напрямую.

```bat
"%IBCMD%" infobase replicate ^
  --dbms=MSSQLServer --database-server=%SRC_SERVER% --database-name=%SRC_DB% ^
  --database-user=%SRC_USER% --database-password="%SRC_PWD%" ^
  --target-dbms=PostgreSQL ^
  --target-database-server=%DST_SERVER% --target-database-name=%DST_DB% ^
  --target-database-user=%DST_USER% --target-database-password="%DST_PWD%" ^
  --target-create-database --force ^
  --jobs-count=%JOBS_SRC% --target-jobs-count=%JOBS_DST%
```

- Запускать там, где ibcmd видит источник: MSSQL-источник — только Windows.
- Пароли не хардкодить: батник спрашивает их через `set /p`, креды живут в
  локальном env или файле вне git.
- `--force` завершает сеансы источника; приёмник пересоздаётся, поэтому
  перезапуск начинает перенос с нуля — прогресс не сохраняется.
- `--jobs-count`/`--target-jobs-count` по умолчанию равны числу логических
  ядер; порция — 10 000 строк или 10 МБ (`--batch-size`, `--batch-data-size`).
- Ход: «Репликация информационной базы…», «Создание информационной базы…»,
  затем «Перенесено таблиц: N»; успех — код 0. Счётчик таблиц слабый
  индикатор (объём сидит в журналах, табличных частях и регистрах), честный
  прогресс — размер целевой базы.
- Скорость упирается в конвертацию строк, порядка 10–20 МБ/с: 100–120 ГБ —
  это 2–4 часа плюс построение индексов. При загрузке всех ядер добавление
  потоков не поможет; если занято одно ядро из многих — можно поднять `-j`/`-J`,
  но только ценой перезапуска.

## PostgreSQL: подготовка приёмника

1. Роль: `CREATE ROLE <user> WITH LOGIN PASSWORD '…' CREATEDB SUPERUSER;`.
   CREATEDB нужен для `--create-database`, SUPERUSER — для инициализации базы
   1С (иначе `permission denied for language c`).
2. Доступ снаружи: строка `host all <user> <подсеть> scram-sha-256` в
   `pg_hba.conf` (путь — `SHOW hba_file;`), `listen_addresses` в
   `postgresql.conf`, затем `SELECT pg_reload_conf();`.
3. Порт не по умолчанию — в имени сервера: `--database-server="host port=6432;"`.
4. Проверка до перелива: `config generation-id` с координатами приёмника.

## Ошибки прямого доступа и их смысл

- **«База данных не найдена» при успешной аутентификации** — логин СУБД есть,
  а пользователя внутри базы нет. Проверка под администратором:
  `USE <db>; SELECT dp.name FROM sys.database_principals dp WHERE dp.name='<user>';`
  Лечение: `CREATE USER <user> FOR LOGIN <user>;`
  `ALTER ROLE db_owner ADD MEMBER <user>;`
- **Аутентификация**: нужен SQL-логин с паролем, Windows-интегрированная не
  годится. `sa` не обязателен: `db_owner` на одну базу даёт внутри неё полные
  права, наружу доступа нет (tempdb доступен всем — 1С держит там временные
  таблицы).
- **Неудачный `--create-database` оставляет полупустую базу** («DATABASE не
  пригоден для использования», `generation-id` падает на чтении служебных
  строк): ibcmd базы не удаляет — удали её руками (`DROP DATABASE …` под
  администратором) и повтори создание. `infobase clear` чистит данные, но
  битую инициализацию не лечит.
- **Кластерная ИБ и unica**: раннер классифицирует подключение `Srvr=…` как
  кластер и отвергает `ibcmd` для `push`/`pull`/`infobase.dump` независимо от
  заполненного `infobases.origin.dbms` (проверено живыми dryRun). Прямой ibcmd
  по СУБД — законный обход с названной причиной; на PostgreSQL он снимает и
  ограничение Linux.

## Сверка src↔база — нормализованно

Метод: свежий `config export` в черновой каталог + `diff -rq` с src.
Канонизация представления — не расхождение: BOM, CRLF, хвостовая новая
строка, порядок секций и составных типов (платформа выравнивает под порядок
родителя), сортировка `Content.xml` при идентичном составе, версии/время
`ConfigDumpInfo.xml`, дописанный пустой `<InternalInfo/>`.

Перед выводом «потеря данных» проверять свойства объекта: `<Code/>` при
`CodeLength=0` — каноничное представление (кодов у справочника нет вовсе),
не потеря. Код предопределённого в исходниках при нулевой длине кода —
стале-артефакт старой выгрузки, ibcmd его нормализует.

## Границы с unica

- `unica.run push` набора с формой с ручным динсписком падает
  `ConfigFilesError` (в том числе на пустой копии ИБ; причина не
  установлена, апстрим unica#1877) — доставка таких форм только ibcmd
  (import → apply --force). Сверку и чтение unica при этом ведёт как обычно.
- apply-поверхность не выражает dcssch-схему полей динсписка (только
  структурные операции; mainTable теряется молча) — правки формы с ручным
  динсписком: документированная эскалация, не unica-поверхность.
- `object.borrow` — только объекты верхнего уровня (частично закрыто
  unica#937).
- unica может отказывать в apply/view целиком на больших конфигурациях:
  git-инспекция сваливается за порогом классифицируемых ресурсов (наблюдалось
  с 128k файлов; «resource classification count exceeds 65536»,
  `readinessState=incomplete`). Режим «unica недоступна» и эскалационный
  канал — docs/UNICA.md плагина; поставка ibcmd от отказа unica не зависит.

## Wayland: платформа не стартует («Unable to initialize GTK+»)

GTK в поставке платформы не поднимает Wayland-бэкенд: 1cv8 (агент Дизайнера,
Конфигуратор) умирает на старте. ibcmd GTK не требует — поставке не мешает.
Рецепт — тень установки с обёртками, путь тени в `tools.platform.path`:

```sh
#!/bin/sh
# build/tools/platform-bin/1cv8 (аналогично 1cv8c, 1cv8s)
unset WAYLAND_DISPLAY
GDK_BACKEND=x11
export GDK_BACKEND
exec /opt/1cv8/x86_64/<версия>/1cv8 "$@"
```

- обёртки для `1cv8`, `1cv8c`, `1cv8s`; `.hbk`-файлы (`1cv8_root.hbk`,
  `1cv8_ru.hbk`, `basicui_*`, `accntui_*`, `bpui_*`) — рядом в тени;
- в `v8project.local.yaml`:

  ```yaml
  tools:
    platform:
      path: '<абс-путь тени>'   # без strict-пина версии
  ```

- тест-клиент на видимый дисплей — тот же корень проблемы, env-паттерн
  скилла `1c-testpilot` (`env -u WAYLAND_DISPLAY DISPLAY=… 1cv8c`).
