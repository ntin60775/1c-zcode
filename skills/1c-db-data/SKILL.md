# Данные базы 1С через MCP 1c-db (1c-mcp-toolkit)

## Анонимизация канала — всегда включена

Ответы инструментов `execute_query`, `execute_code`, `get_object_by_link`,
`get_event_log`, `find_references_to_object`, `get_access_rights`
токенизируются прокси: персональные и конфиденциальные данные приходят как
`[ORG-00001]`, `[INN-00001]`, `[PHONE-00001]`, `[PER-00001]` и т.д. Это норма,
а не поломка. Работать с базой без анонимизации запрещено.

- Токены детерминированы в рамках сессии: подставляй их в параметры следующих
  запросов — прокси восстановит реальные значения перед исполнением в 1С.
  Параметры `execute_query` передаются ключом **`params`** (не `parameters` —
  молча потеряется).
- **Прогрев обязателен после каждого подъёма канала.** На холодном старте
  прелоад словаря упирается в таймауты (медленный коннект epf), словарь
  собирается частичным, и значения вне словаря уходят в ответ СЫРЫМИ.
  Прогрев: запрос первых строк Контрагентов —
  увидел `[ORG-…]`/`[INN-…]` — словарь готов; увидел сырое наименование/ИНН —
  канал считать не готовым: реальной работы не вести, сообщить владельцу,
  полностью перезапустить канал (клиент + прокси) и повторить прогрев.
- **Приёмочный набор канала** (после прогрева):
  ЖР через `get_event_log` (ЖурналРегистрации в execute_query недоступен —
  «таблица не найдена»), по 5 самых новых `Документ.ЗаказКлиента` и
  `Документ.РеализацияТоваровУслуг` (в базе может не быть — фиксировать
  факт, не выдумывать). Смотреть представления ссылок (Контрагент и т.п.) —
  обязаны быть токенами; номера и суммы документов идут как есть.
- Полный контекст (категории, правила) — `ANONYMIZATION.md` клона
  1c-mcp-toolkit. Словарь собирается из Контрагентов/Организаций/
  ФизическихЛиц/Сотрудников/Пользователей базы при старте прокси.
- Отключение (`CONTOUR_ANON=off`) — только e2e-прогоны (`run_e2e.sh` делает
  это сам и возвращает анонимизированный стенд после). В интерактивной
  сессии не отключай; увидел в ответах сырые ИНН/телефоны/наименования —
  канал поднят без анонимизации, сообщи владельцу и перезапусти стенд
  (`start_1c_db.sh <root> --stop` → `--headless`).

Адрес сервера `1c-db` — из `.zcode/1c/contour.json` (ключ `1c_db.url`);
порт не константа — у каждого проекта он свой, не подставляй его из головы.
Несколько баз на машине — это каналы одного прокси (`?channel=` в url);
разнесённые стенды — свои `1c_db.url` в contour.json каждого проекта.
Архитектура платформозависима: **встроенный HTTP-транспорт тулкита —
Windows-DLL**; на Linux endpoint держит python-прокси
`onec_mcp_toolkit_proxy`, а клиент 1С подключается к нему сам (long-poll).
Подъём — одной командой, без ручных кликов в форме:

```bash
# один раз на машину:
<контур>/scripts/install_1c_mcp_proxy.sh <клон-1c-mcp-toolkit>
# поднять (Linux: прокси + клиент mode=proxy; Windows: embedded):
bash .zcode/1c/scripts/start_1c_db.sh .    # --headless: Xvfb + WM
```

Креды базе не нужны — обработка уже внутри сессии. REST `/api/*` того же
прокси — curl-fallback без MCP.

## Первая/перезалитая база: разовое подтверждение на видимом дисплее

Первая живая сессия клиента в **новой** базе упирается в диалоги платформы
(подтверждение NativeAPI-компоненты тулкита, аутентификация, если есть
пользователи) — headless-клиент их не проходит и молча висит. Это
предсказуемый шаг, а не поломка: подтверждение делается **руками владельца
один раз на базу** и наследуется клонами. Триггер — база создана с нуля или
в существующий контур залили другую базу (`*.dt`, пересозданный `build/ib`):
живой контур не освобождает от ритуала, подтверждение привязано к базе, не
к контуру.

Порядок (до headless-стенда и любых проверок тест-контура):

```bash
# видимый дисплей владельца — из contour.json → 1c.display.visible
# (нет ключа — спроси адрес у владельца; :1 — типовой X-дисплей сессии):
DISPLAY=<видимый> bash .zcode/1c/scripts/start_1c_db.sh .    # БЕЗ --headless
# владелец проходит диалоги в окне клиента → клиент «опрашивает прокси»
bash .zcode/1c/scripts/start_1c_db.sh . --stop               # погасить
bash .zcode/1c/scripts/start_1c_db.sh . --headless           # штатный стенд
```

Не пропускай шаг на новой/перезалитой базе: headless-подъём без ритуала
не подключается, а разбор «сломанного» стенда дороже минуты ритуала
(в `start_1c_db.sh` это же — первая строка диагностики таймаута).

Тут же, в открытом окне клиента, оператор настраивает **профиль правил
анонимизации** (вкладка «Анонимизация» → «Правила анонимизации…»):
профиль по умолчанию закрывает мало — отметить нужные объекты и поля,
«Сохранить настройки». **Перезаливка базы (`*.dt`, пересозданный
`build/ib`) стирает сохранённые настройки вместе с профилем** — при
обновлении/загрузке новой копии базы профиль восстанавливается из файла
(«Загрузить из файла») или настраивается заново; поэтому набор хранят
файлом («Сохранить в файл»). Вместе с профилем стираются доверие epf
(диалог безопасности заново) и настройки канала (фаза 1 startup их
перезапишет; danger-флаги ставит фаза 2 автоматически). Ручной шаг
наравне с подтверждениями.

## Диагностика зависаний и гашение стенда

**Скрин — первым делом.** Клиент не подключился за ~60 с или фаза
`wait_client` тикает — не жди вслепую и не смотри только на `ps`/CPU:
немедленно сними виртуальный дисплей и посмотри, что реально на экране:

```bash
DISPLAY=:97 import -window root /tmp/screen.png   # весь дисплей
# конкретное окно (сплэш/диалог):
W=$(DISPLAY=:97 xdotool search --name '^1С:Предприятие$' | head -1)
DISPLAY=:97 import -window "$W" /tmp/window.png
```

Картинка сразу разделяет причины: прогресс «Загрузка информационной
базы» — база реально читается, жди; модальный диалог (безопасность epf,
подтверждение компоненты, аутентификация) — под WM он виден на :97, кликай
xdotool'ом по координатам скрина или поднимай клиента на видимом дисплее
оператора (ритуал выше), а без WM диалог невидим и клиент висит вечно.
Открылась форма тулкита со статусом «Подключение…» и poll отсутствует —
ищи модальность/причину в форме, а не в сети.

**Тяжёлая база грузится дольше дедлайна фазы.** `WAIT_DEADLINE` (420 с) —
потолок ожидания скрипта, а не загрузки: скрипт честно падает exit 1, но
клиент продолжает грузиться сам. Критерий готовности — poll-запросы в
логе прокси (`GET /1c/poll`), а не код возврата скрипта. Не перезапускай
клиента при долгой загрузке — перезапуск сбрасывает прогресс. Если
загрузка замерла (CPU перестал расти при прочитанной базе) — это не
«долго», это зависание: скрин, разбор, при воспроизводимости — ишью.

**Гашение — короткими командами с перепроверкой.** Гаси процессы
короткой командой `kill -9 <pid>…` и обязательно проверяй результат
отдельной свежей командой `pgrep -af …`: успешный код возврата kill и
«чисто» из той же составной команды не доказывают смерть процессов
(сигналы из длинных составных команд порой не доставляются — подозрение
на рантайм эджента, до выяснения обходится дисциплиной). Цепочка
distrobox/podman-обёрток умирает с задержкой и волнами — добивай и
перепроверяй.

**Headless-подъём идёт на полноценном невидимом дисплее: Xvfb + WM.** Без
оконного менеджера платформа не отрисовывает модальные диалоги и клиент
вечно ждёт ответа: UI не рисуется (чёрная форма или «Подключение…» с
баннером «При обновлении конфигурации произошла ошибка»), poll к прокси
не начинается. Скрипт сам поднимает WM — первый доступный из
xfwm4/openbox/fluxbox/jwm/metacity/marco/i3/twm (работающий WM на :97
переиспользуется; лог `/tmp/1c-db-wm-<hash>.log`) — и предупреждает в
stderr, если WM не найден: такой стенд не поднимай, сначала поставь любой
WM. Модальные вопросы безопасности («Разрешить подключать бинарный файл?»,
«Разрешить администрировать пользователей?») выдаются на базу+пользователя
и персистентны; сбрасываются чисткой клиентского кэша, перезаливкой базы и
сдвигом версии конфигурации (см. «Первая/перезалитая база» выше). Под WM
диалог виден на :97 — кликай xdotool'ом по координатам со скрина (1 пиксель
= 1 координата) или проводи первый запуск на видимом дисплее владельца.
Программно подавить вопросы нельзя: флаг пользователя
`ЗащитаОтОпасныхДействий.ПредупреждатьОбОпасныхДействиях` на
ERP2-конфигурации не действует (конфигурация форсирует защиту).

**Техжурнал платформы — только на время разбора, всегда убирай за собой.**
Конфиг клиент берёт из `/opt/1cv8/conf/logcfg.xml` в контейнере (путь задаёт
`ConfLocation` в `conf.cfg` версии платформы), не из `~/.1cv8/conf`; каталог
`location` создай заранее — платформа сама его не создаёт; «все события» =
фильтр `<event><ne property="name" value=""/></event>` — `<log>` без
event-фильтров пишет пустой журнал. Лог режется почасам (`26102914.log` =
ГГММДДЧЧ): недописанный часовой файл выглядит как «обрыв активности» —
выводы о «тишине» делай после смены часа или гашения клиента. Объём
~180 МБ/час. Закончив разбор и гася стенд, всегда удаляй `logcfg.xml` и
каталог логов: включённый техжурнал за живым клиентом — незакрытая работа.
ЖР живого стенда читай `get_event_log` (двойной JSON-слой в ответе, лимит
1000, имена событий — точными строками `_$Session$_.Authentication` и
т.п.). Активность сеансов по файловой базе не оценивай по mtime
`1Cv8.1CD`: ЖР лежит в `build/ib/1Cv8Log/*.lgp` и клиент пишет туда
лениво — файл базы может не меняться при живых сеансах.

**Пути и имена баз — программно.** Кириллические имена каталогов
(«через в»/«через г» и т.п.) дают опечатки, неотличимые на глаз: путь к
базе всегда бери из конфига/профиля или листинга программно, не набирай
руками. Тест-клиент testpilot руками (`1cv8c /TESTCLIENT …`) не
поднимается — только раннером 1c-testpilot (см. скилл 1c-testpilot).

## Обновление обработки (epf): ручные шаги оператора на каждой базе

Замена файла `MCP_Toolkit.epf` (любой новый контент — обновление донора
1c-mcp-toolkit, ребилд) сбрасывает доверие платформы к пути: 1С показывает
диалог «Предупреждение безопасности: Разрешить открывать данный файл?».
Без WM диалог невидим — клиент вечно «грузится», канал молчит; под
штатным `--headless` (Xvfb + WM) он виден на :97 — клик «Да» xdotool'ом
по координатам скрина (headless-раздел выше). Клики в 1С на видимом
дисплее — действие оператора; первый запуск новой/перезалитой базы —
ритуал на видимом дисплее (выше).

Порядок обновления:

1. Прокси и epf — парой строго с одного тега клона: обнови клон на тег,
   сверяй requirements (менялись — перегони venv через
   `install_1c_mcp_proxy.sh`). Файл обработки — **под ОС хоста**
   (ROCTUP/1c-mcp-toolkit#34): Linux →
   `MCP_Toolkit_linux.epf`, Windows → `MCP_Toolkit.epf`, macOS →
   `MCP_Toolkit_macos.epf` (x86-вариант — для 32-битной платформы).
   Раннер `start_1c_db.sh` выбирает файл по ОС сам и при
   отсутствии доставляет его: `build/` клона → релиз GitHub того же
   тега. Явный `1c_db.epf_path` в contour.json перекрывает детект.
   Замену уже лежащего файла автоматом раннер не делает — доверие
   платформы к пути и клики оператора остаются ручным шагом (выше).
   Линукс-файл в локальном `build/` клона не собирается — он только
   в assets релиза тега; если сети нет, скачай заранее.
2. Старую версию вычисти везде: копий старого epf в проекте и на стенде
   не оставляй; после живой проверки новой версии снеси откатные копии
   в том же заходе.
3. **Запуск — `start_1c_db.sh` делает обе фазы сам**: фаза 1 —
   startup на видимом дисплее оператора (как в ритуале первой базы выше;
   диалог безопасности → «Да», база запоминает настройки канала), фаза 2 —
   автоматический перезапуск с `/C "autostart;<метка
   yyyyMMddHHmmss>;<params.json>"` (`danger_auto_write`/`danger_auto_priv`
   = true, файлы владения, окно 300 с, связь из сохранённых настроек) —
   флаги «Автоматически разрешать операции» включаются без кликов, словарь
   анонимации прогревается. Отключить фазу 2: `CONTOUR_AUTOSTART=off`.
4. **Профиль правил анонимизации — ручной шаг оператора**: вкладка
   «Анонимизация» → «Правила анонимизации…» — профиль по умолчанию
   закрывает мало; оператор
   отмечает нужные объекты/поля сам и жмёт «Сохранить настройки»
   (живёт в сохранённых настройках базы). Набор можно хранить файлом
   («Сохранить в файл» → на других базах «Загрузить из файла») — тоже
   вручную. Явные правила действуют только на `execute_query`;
   переключатель Все/Да/Нет/Не задано над деревом — фильтр просмотра,
   не установка значений.
5. Дождись подъёма канала, прогони пробы (запрос, токены анонимизации на
   Контрагентах, новинки релиза), затем верни штатный headless-стенд
   (`--stop` → `--headless`).

Файл обработки — строго под ОС хоста. Признак чужого ОС файла на Linux:
канал живой, но лог ругается «QueryLineageAnalyzer не загружена», а
линукс-компоненты отсутствуют — поставь `MCP_Toolkit_linux.epf`.
Инструмента `schema.sources` нет в любой сборке v1.9.0 (12 инструментов
без schema-группы) — его отсутствие не признак деградации.

## Инструменты (читающие — основной набор)

| Инструмент | Зачем |
|---|---|
| `execute_query` | язык запросов 1С: данные, сверки, фикстуры e2e |
| `get_metadata` | структура метаданных объекта (реквизиты, табличные части) |
| `get_event_log` | журнал регистрации: ошибки, предупреждения, история — ЖР-сверка e2e-прогонов |
| `find_references_to_object` | кто ссылается на объект — оценка последствий правки |
| `get_object_by_link` / `get_link_of_object` | чтение/адресация объектов по навигационной ссылке `e1cib/data/…` |
| `get_access_rights` | проверка прав роли на объект |
| `get_bsl_syntax_help` | справка синтаксиса изнутри сессии |

Изменяющие (`execute_code`, `submit_for_deanonymization`,
`restart_1c_session`, `close_1c_session`) в прод-контуре блокируются гейтом
`mcp-unsafe-gate` (fail-closed); в тестовом (`contour: test`) свободны.

## Правила запросов (execute_query)

- Пиши запрос целиком, параметры — через `&Параметр`, не конкатенацией строк.
- Сначала запрос схемы (`ВЫБРАТЬ ПЕРВЫЕ 1`), потом полный — не тяни таблицы
  целиком: ЖР и регистры бывают гигантские.
- Для ЖР-сверки e2e: окно времени бери из сводки прогона workflow
  `1c-e2e-run`, фильтруй `ТипУведомления В (Error, Fatal)`.
- Результат большой — агрегируй в запросе (СЧЁТ, СУММА), не выгружай строки.

## REST-fallback (curl, без MCP)

Обработка публикует те же операции на `/api/*`:

```bash
curl -s http://127.0.0.1:6003/api/execute_query \
  -H 'Content-Type: application/json' \
  -d '{"query": "ВЫБРАТЬ ПЕРВЫЕ 5 Наименование ИЗ Справочник.Номенклатура"}'
```

Опасные REST-операции (`execute_code` и др.) гейт распознаёт и в bash —
прод-контур блокируется одинаково.

## Фикстуры e2e-тестов

Данные для сценария — из реальной базы (`execute_query`), а не выдуманные:
сценарий должен находить то, что существует. Мутирующие подготовительные
операции — только в тестовом контуре; на проде фикстуру согласуй с
пользователем.
