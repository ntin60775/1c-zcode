# Ревью BSL: стайл-пак + стандарты

Единственный формальный ревьюер BSL-правки. Два домена требований:

- **Домен A — стайл-пак `1c-bsl-code-style`** (вендорен в
  `.zcode/skills/1c-bsl-code-style/`): форма кода, naming, doc-comments,
  дробление методов, промежуточные переменные. Источник требований — сам
  пак, ревьюер применяет их, не создавая собственных правил стиля.
- **Домен B — стандарты платформы (v8std)**: находки детектит `unica.check`
  (bsl-analyzer), ground truth — `unica.docs {source: development-standard}`
  в момент ревью; тексты стандартов в навыке не хранятся, только std-id.

При расхождении доменов в одной точке приоритет у стайл-пака — правило
закреплено контуром; расхождение фиксируется в отчёте строкой, не молча.
Компиляция и поведение — вне обоих доменов, их держит гейт запуска
(загрузка конфигурации платформой, живая проба / e2e); вердикт `risk` не
перекрывается ни приоритетом домена, ни журналом исключений.

Ревьюер — протокол того же агента, что делал правку, а не отдельный
субъект: ревью — контрольная точка перед отчётом о завершении;
замечания к коду задачи гасятся той же сессией в автономном цикле
(шаг 10), оператору даётся только финальный отчёт.

## Незыблемое (поставляемость и агностичность)

- Навык не содержит проектных фактов: ни разрешённых методов, ни списков
  подсистем или модулей, ни порогов. Всё проектное входит через журнал
  исключений (references/exceptions-contract.md) и факты метаданных
  (`unica.view`).
- Подсказка аналайзера — не требование, а указатель. За каждой подсказкой
  вида «используйте X.Y» ревьюер обязан: (а) проверить, существует ли модуль
  X в этой конфигурации; (б) открыть стандарт, стоящий за диагностикой.
  Подсказка может звать в модуль, которого в проекте нет.
- Диагностика, которой нет в таблице маршрутизации, — класс `unknown`:
  раскрыть через `unica.docs`, вынести вердикт, предложить строку таблицы
  ишью в контур. Таблица самопополняемая, процедура неизменна.

## Порядок работы

Порядок ступенчатый: машинное раньше процедурного (дёшево и
детерминированно), гашение журналом раньше раскрытия стандартов (не
открывать docs для исключённого), факты метаданных — только там, где класс
требует, конфликт доменов — после того, как обе стороны сформулированы.

1. **Scope**: изменённые BSL-узлы (из diff или журнала `unica.apply`);
  неизменённый код — фоном, не блокирует.
2. **Домен A, машинная часть**: вывод стайл-гейта (`bsl-style-gate` после
  правок `.bsl`; внутри — чекер `bsl_style_check.py` пака, находки вида
  `путь:строка: [id]`; закоммиченное — прогнать чекером по изменённым
  файлам). Находки — вердикт `fix`, основание — правило чекера.
3. **Домен A, процедурная часть**: применить к изменённым участкам
  требования вендоренного пака сверх машинных правил — шапка модуля,
  дробление методов, промежуточные переменные, doc-comments, naming,
  включая делегированные паком частные правила #std647: глагольная форма
  процедуры, имя функции от возвращаемого значения, `Новый…`, `Это…`,
  исключения 6.4/6.5 (references/naming.md пака). Основание вердикта —
  файл и секция пака.
4. **Домен B, детекция**: `unica.check {}` даёт вердикт workspace и группы
   диагностик страницами — это триаж; детальные находки — `unica.check {at}`
   по каждому узлу. Пока в ответе есть `cursor`, страница не последняя:
   дочитай тем же `at`/`limit`, иначе вывод о полноте ложный. Каждая
   диагностика — через references/routing.md:
   код → класс → действие по умолчанию → std-id → блокер или нет.
   Страницы одного узла можно прогнать скриптом-джойном
   `.zcode/1c/scripts/bsl_review_join.py` (сохранённые ответы `unica.check`
   × routing × журнал исключений → размеченные находки и строки отчёта):
   он делает маршрутизацию и гашение журналом этого и следующего шага.
   Джойн ускоряет шаги 4–5; его отсутствие процедуру не ломает — обе
   ступени выполняются руками.
5. **Журнал исключений**: `.zcode/1c/standards-exceptions.yaml` (формат и
  семантика — references/exceptions-contract.md). Совпадение гасит находку
  домена B вердиктом `waived` до раскрытия; в отчёте — одной строкой.
  Файла нет — все находки живые; отсутствие легально. Незнакомая версия
  формата — остановить сверку и сообщить (fail-closed).
6. **Раскрытие и компиляционная сверка** (живые находки домена B):
   `unica.docs` по std-id — требование и платформенный эквивалент
   (`platform-help` / `development-standard`; `configuration-documentation`
   в 0.15 отвечает `unsupported_source`). Каждая подсказка «используйте
   X.Y» сверяется с метаданными (`unica.view main:CommonModule.X`,
   `unica.search`). Буквальный поиск идёт страницами до последнего
   совпадения, первая страница несёт `data.totals`: пока есть `cursor`,
   вывод «не найдено» неполон. Модуля нет — вердикт `risk` +
   платформенный эквивалент из docs; `risk` гасится только правкой.
7. **Конфликт доменов**: одна точка, требования расходятся — выполняется
  требование пака; в отчёте строка «#std… отклонён приоритетом
  стайл-пака, основание — <файл пака>». Для кода этой задачи отклонений
  от требований пака не оставляют — правка по паку, цикл до нуля;
  «осознанно оставляем» — только унаследованный код и только решением
  владельца; правило плохое — ишью в пак.
8. **Отчёт**: по строке на находку — источник (пак / диагностика) →
  требование → вердикт → основание; завершающая строка, чем
  верифицирована компиляция (загрузка конфигурации, живая проба — или
  «не выполнено»).
9. **Принятые владельцем `waived`** предлагать к внесению в журнал, готовя
  текст записи; файл журнала без команды владельца не менять.
10. **Цикл устранения** (автономный, оператор не участвует): каждое
  открытое замечание к коду этой задачи → правка через `unica.apply` →
  повторный прогон ревью по затронутым узлам — пока открытых замечаний
  не останется. Цикл не останавливают: совпадение с журналом исключений
  (решение уже принято, применяется автоматически), analyzer-noise
  (гасится сверкой с эталоном), `report`-класс (строка в отчёте,
  действия не требует). Остановка с эскалацией — только два случая:
  metadata-класс (флаги модуля — метаданные, правка кода не лечит) и
  невозможность стандартно-корректной правки без ломки намеренной
  семантики задачи (редкий случай — в финальный отчёт уходит предложение
  записи журнала, не молчаливая полумера). Финальный отчёт владельцу:
  чистый прогон, перечень `report`/`waived`, предложенные записи журнала.
  Отдельное решение о сроках и исполнителе — только для ревью по команде
  владельца над готовым или замороженным кодом, не правкой этой сессии.

## Вердикты

- `fix` — нарушение, требуется правка; для кода текущей задачи
  исправляется в автономном цикле (шаг 10), оператору — финальный отчёт.
- `risk` — не скомпилируется / не выполнится; гасится только правкой.
- `waived` — осознанное проектное исключение из журнала; применяется
  автоматически, в отчёте одной строкой; новые записи — предложение в
  финальном отчёте, файл меняет владелец.
- `report` — замечание без обязательного действия (метрики,
  производительность запросов); строка в финальном отчёте.

## Протокол вызова (секция «Качество кода» контура)

Любая BSL-правка: guard `bsl-style-gate` при правке; настоящий навык —
перед отчётом о завершении и перед push, оба домена обязательны. Пропуск
любого из двух — отклонение от процедуры, а не вопрос усмотрения.

## Границы

- Общее код-ревью (дефекты, регрессии, риски, тесты) — `unica:code-review`.
- Вызовы БСП при внедрённой БСП — скилл `bsp` (БСП 3.1.11).
- Компиляция и поведение — только гейт запуска: загрузка конфигурации
  платформой, живая проба / e2e. Настоящий ревьюер их не заменяет.
