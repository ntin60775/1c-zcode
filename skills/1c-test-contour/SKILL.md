# E2E-тест-контур 1С (1c-testpilot)

## Философия: внешний оракул

Сценарий и ассерты пишет агент — значит, самопроверка слабая. Контур требует
внешних доказательств:

1. **Record-first**: канонический сценарий записывается с человеческой сессии
   (`tc_scenario` запись → XML), агент параметризует и реплаит. С нуля шаги
   не сочиняются.
2. **Readback**: каждое изменение формы подтверждается ответом инструмента
   (`value_before` / `value_after`) — «нажал и надеюсь» не проверка.
3. **ЖР-сверка**: после операции журнал регистрации сканируется на
   `Error`/`Fatal` (через `get_event_log` MCP `1c-db`). Тихие ошибки форм —
   частый источник ложно-зелёных прогонов.
4. **Анти-ложно-зелёная приёмка**: прогон с нулём проверок или без ЖР-сверки —
   красный. Это правило исполняет код workflow `1c-e2e-run`, не добрая воля.

## Канонический поток

```
tc_session launch_client(profile=…)   # поднять тест-клиент
tc_find wait …                         # дождаться элемента
tc_window execute_command …           # команды окна/формы
tc_field get/set …                     # поля: set возвращает readback
tc_table …                             # таблицы форм
tc_session close                       # закрыть приложение
tc_session stop_client                 # погасить тест-клиент
```

- Базовый набор инструментов: `tc_session, tc_find, tc_window, tc_field,
  tc_table`. Прочие группы тяни точечно — их схемы дороги (~21 тыс. токенов
  все 10 групп).
- Профили баз — `.zcode/testpilot/profiles.yaml` (пароли только через
  `password_env`).
- Опциональные exec-группы (`tc_execute_code` и др.) выключены env
  контура; их включение — осознанная правка `.zcode/config.json`.

## Workflows (исполнение — кодом, не прозой)

- **`1c-e2e-run`** — прогон сценария/набора: субагент-тестировщик гонит и
  возвращает readback-доказательства → независимый сверщик читает ЖР →
  вердикт (нулёвые проверки / без ЖР-сверки / ошибки = красный) считает код
  workflow → markdown-отчёт. Запуск: имя workflow + аргументы
  `scenario` (путь к XML) и `profile`.
- **`1c-e2e-record`** — запись нового сценария: оператор поднимает клиент и
  запись, человек водит сессию, агент сохраняет XML в
  `.zcode/testpilot/scenarios/` и доказывает воспроизводимость реплеем.

Routine-прогон записанного набора в CI — pytest-плагином testpilot
(`pytest --tc-profile=main`), без модели.

## Грабли (перенос из практики agent-kit, MIT)

- Не доверяй «выполнено» без readback: тест-клиент отвечает успехом на
  команду, даже если форма её не отрисовала.
- Изолированный рабочий стол (`desktop: isolated`) обязателен на Linux —
  иначе тест-клиент ловит фокус реальной сессии.
- Долгие операции — `tc_find wait` с таймаутом, а не сон между шагами.
- Сценарий зависит от данных: перед прогоном убедись, что фикстура на месте
  (данные реальной базы — скилл `1c-db-data`), иначе шаг честно не найдёт
  элемент.
