# E2E-тест-контур 1С (1c-testpilot, write-first)

## Философия: тест пишет агент, оракул — внешний

«Записать сценарий с человеческой сессии» в контуре нет: носитель сценария —
код в `tests/e2e/`, который агент пишет сам и сам прогоняет. Человек не нажимает
ничего: тест-клиент testpilot поднимается сам по профилю (`base` в
`.zcode/testpilot/profiles.yaml`; на Linux `desktop: isolated` — приватный
Xvfb на каждый запуск) и сам гасится после прогона.

Самопроверка агента слабая, поэтому приёмка требует внешних доказательств:

1. **Readback**: каждое изменение формы подтверждается чтением
   (`get_text()` / `get_data_presentation()` / `get_context()`) — «нажал и
   надеюсь» не проверка.
2. **ЖР-сверка**: журнал регистрации сканируется на `Error`/`Fatal`
   (MCP `1c-db`, `get_event_log`). Тихие ошибки форм — частый источник
   ложно-зелёных прогонов.
3. **Анти-ложно-зелёная приёмка**: ноль собранных тестов или прогон без
   ЖР-сверки = красный. Правило исполняет код workflow `1c-e2e-run`, не
   добрая воля.

## Два способа управлять клиентом

- **Python API (основной, автономный)**: `from testpilot import Client` —
  тот же клиент тестирования, но без MCP и без модели. Носитель теста и
  способ разведки. Прогон — `scripts/run_e2e.sh` (pytest, равный CI).
- **MCP `tc_*` (интерактивный)**: когда модель водит клиент в реальном
  времени — разовая диагностика живой формы, uilog-smoke. Базовый набор:
  `tc_session, tc_find, tc_window, tc_field, tc_table`; прочие группы —
  точечно, их схемы дороги. Опциональные exec-группы (`tc_execute_code`)
  выключены env контура; включение — осознанная правка `.zcode/config.json`.

## Написание e2e-теста (канон автора)

1. **Разведка — живьём, не по памяти**:
   ```bash
   TC1C_PROFILES_FILE=.zcode/testpilot/profiles.yaml \
     ~/.local/venvs/1c-testpilot/bin/python -c '
   from testpilot import Client
   c = Client(profile="main")            # сам поднимет тест-клиент
   c.execute_command(command="e1cib/list/Справочник.X")  # список, не data!
   form = c.find_object(cls="ManagedForm", timeout=30)
   print(form.get_context())             # имена формы и элементов
   c.close(); c.stop_client()'           # не оставлять клиента висеть
   ```
2. **Тест**: fixture `testpilot` (pytest-плагин регистрируется с пакетом),
   проверка имени формы (`get_context()["form"]["form_name"]`) отличает
   целевую карточку от неожиданного диалога:
   ```python
   import pytest

   @pytest.fixture
   def form(testpilot):
       testpilot.execute_command(command="e1cib/list/Справочник.X")  # список!
       f = testpilot.find_object(cls="ManagedForm", timeout=30)
       assert f.get_context()["form"]["form_name"].startswith("Справочник.X.")
       return f

   def test_smoke(testpilot, form):
       field = form.find_object(name="Наименование")
       field.input_text(text="Е2Е-проверка")
       assert field.get_data_presentation() == "Е2Е-проверка"
   ```
3. **Данные**: создавай с уникальным маркером («Е2Е-» + дата-время), в конце
   удаляй созданное. Чужие данные не мутируй. Фикстура на месте до прогона?
   Проверь через `1c-db` (`execute_query`, скилл `1c-db-data`).
   Маркер обязан попадать в Наименование (справочники) и Номер (документы) —
   только их находит sweep. `run_e2e.sh` после прогона сам ищет остатки по
   маркеру, удаляет их (`e2e_sweep`) и красит прогон (exit 3), если вычистить
   не удалось. Регистры sweep не покрывает — чистить финализатором.
4. **Прогон**: `bash .zcode/1c/scripts/run_e2e.sh [профиль] [tests/e2e]` —
   pytest без модели, junit в `test-results/`; хвост `E2E_SUMMARY_JSON {...}`
   парсят workflow. Коды выхода: 0 — зелёный и база чистая; 3 — pytest
   зелёный, но остатки `Е2Е-`-данных не вычистились (считай прогон красным,
   почини тесты или базу); 2 — окружение/прокси не готовы. Пароль берётся из
   окружения (`password_env` профиля) или из `v8project.local.yaml`.
5. **uilog для разового smoke** (не носитель регресса):
   `tc_scenario(record_start)` → шаги → `record_finish` возвращает XML +
   `lost_actions` (непустой список = сценарий неполный) → реплей
   `run_scenario`. Режим `synth` (по умолчанию) собирает сценарий из вызовов
   агента — «запись» без человека.

## API-контур (HTTP-сервисы, OData)

API-слой гоняется без GUI: публикация тестовой базы + тот же pytest.

1. **Публикация** — автономный сервер 1С (`ibsrv`), без Apache и root:
   ```bash
   bash .zcode/1c/scripts/publish_ib.sh start   # печатает E2E_PUBLISH_JSON {url, port, pid}
   bash .zcode/1c/scripts/publish_ib.sh stop
   ```
   База — `build/ib` (аргументом можно другую); порт — `contour.json →
   1c.publish.port`; сервер слушает только `127.0.0.1`, регламентные задания
   выключены. Резолв ibsrv: env `PUBLISH_IBSRV` → `contour.json 1c.publish.ibsrv`
   (`distrobox:<имя>` — только этот контейнер, `distrobox:auto` — поиск по
   живым контейнерам, иначе путь/готовая команда) → при пустом значении:
   `/opt/1cv8/x86_64/*/ibsrv` → живой distrobox-контейнер.
2. **Тест** — обычный requests; URL и креды не хардкодятся:
   ```python
   import os, pytest, requests

   BASE = os.environ.get("PUBLISH_URL", "").rstrip("/")

   def test_service():
       assert BASE, "публикация не поднята: bash .zcode/1c/scripts/publish_ib.sh start"
       r = requests.get(f"{BASE}/hs/<имя>/<адрес>", auth=(USER, PWD), timeout=60)
       assert r.status_code == 200
       assert r.json()["ok"] is True
   ```
   Креды — из окружения (`password_env`/экспорт), не в коде. `pytest.skip`
   для упавшей публикации не использовать: прогон без живого API — красный.
3. **Оракул тот же**: ЖР-сверка после прогона (workflow делает сам).
   API-тесты лежат в `tests/e2e/` рядом с GUI и гоняются одним
   `run_e2e.sh` — GUI-фикстура (`testpilot`) поднимает клиент только в
   GUI-тестах.

## Три уровня тестов (все — pytest в tests/e2e/, один run_e2e.sh, один ЖР-оракул)

| Уровень | Инструмент | Что проверяет |
|---|---|---|
| Логика | `onec_db` фикстура (execute_code) | инварианты модулей, расчёты, проверки заполнения — то, что защищали юниты yAxUnit |
| API | requests (HTTP-публикация) | HTTP/Web-сервисы, OData |
| GUI | Python API 1c-testpilot | пользовательский путь: формы, документы, таблицы |

Выбор уровня при переносе старых юнит-проверок: чистая логика модуля →
**логика** (дешевле, точнее); интеракция пользователя → **GUI**; сомневаешься —
логика + один GUI-smoke на весь путь.

### Канон логика-теста

Фикстуры `onec_db` / `stub_server` даёт pip-пакет
[1c-onec-db](https://github.com/ntin60775/1c-onec-db) (pytest-плагин, ставит
`scripts/install_testpilot.sh`) — conftest в проекте не нужен. Подключение —
MCP `1c-db` (клиент: `bash .zcode/1c/scripts/start_1c_db.sh`; в проде
execute_code блокирован гейтом — уровень только на тестовых деревьях).
BSL выполняется на сервере, результат читается из переменной `Результат`;
сложные значения возвращай JSON-строкой и парси в тесте:

```python
def test_проверка_суммы(onec_db, json):
    data = onec_db.execute("""
        Если Не ОбщегоНазначения.СуществуетОбщийМодуль("Расчёты") Тогда
            ВызватьИсключение "нет модуля Расчёты";
        КонецЕсли;
        Результат = ЗаписатьJSON(Новый ЗаписьJSON, Расчёты.СуммаСНДС(62000));
    """)
    assert json.loads(data) == 10333.34
```

Первый старт клиента под Xvfb — до ~3 минут (software-GL): это норма, не поломка.

### Моки и тестовые данные (замена юнит-моков)

Классической изоляции (подмена объектов) в 1С не существует даже в yAxUnit —
там «моки» это генерация данных и подмена адресов. Уровень логики даёт те же
две механики, плюс заглушку сети:

1. **Данные-фикстуры**: `onec_db.create_object("Контрагенты",
   {"Наименование": "МокТест", "ИНН": …})` → GUID; в конце —
   `onec_db.delete_object(...)` (созданное помечается «Е2Е-»). Проверяемая
   функция вызывается на этих данных — инвариант без GUI.
2. **Мок внешней системы**: фикстура `stub_server` (локальный HTTP на
   127.0.0.1, маршруты `(method, path) → (status, body)`, журнал обращений в
   `.calls`). Канон интеграций: конфигурация читает базовый URL из
   константы/настройки — тест ставит `onec_db.set_constant(имя, stub_server.url)`
   и получает детерминированный ответ + проверку параметров вызова.
3. **Чистые расчёты** моков не требуют: вызывай функцию — проверяй результат
   (`execute_json`).

Контракт результата: BSL устанавливает переменную `Результат`; сложные
значения — `ЗаписатьJSON` (в тесте `json.loads`); `query()` возвращает
`{"success", "data": [строки]}`. Сгенерированные переменные в BSL — с
префиксом `Е2Е` (`Объект` в окружении Выполнить резолвится в реквизит формы
тулкита — «Элемент не выбран»); создание объектов — только менеджерный путь
(`Справочники.X.СоздатьЭлемент()`). Тестовый прокси разрешает
`Записать`/`Удалить` (данные фикстур); COM/файлы/монопольный режим —
заблокированы всегда. Прод защищён независимо (`mcp_gate`).

## Перенос старых сценариев (Vanessa/xUnit)

Старый стек (Vanessa-Automation + yAxUnit) контуром не поддерживается;
после миграции активы лежат в `docs/omp-migrated/tests/`:

- **`features/*.feature` — только источник.** Конвертация — по канону
  write-first: одна фича = один `tests/e2e/test_<имя>.py`; шаги
  Дано/Когда/Тогда раскрываются через живую разведку формы (имена элементов
  фичи устаревают — проверяй по `get_context()`); параметры из
  `VAParams.json` вписываются в тест значениями; данные с маркером «Е2Е-» и
  очисткой. Прогон до зелёного → `git rm` фичи из архива → коммит. Пока
  фича в архиве — она документация, не исполняемый тест.
- **Юнит-тесты (yAxUnit, расширение «Тесты») не переносятся как код** — но
  защищённая ими логика переезжает полностью: инварианты модулей →
  логика-тесты (`onec_db`), пользовательские пути → GUI-e2e. После переноса
  всех проверок source-set «Тесты» сносится. Смысловые проверки не
  выбрасывать: каждая — регресс, который контур обязан защищать.
- Ключи старого стека в `v8project.yaml` (`tests:` с yaxunit/va, va-подблоки)
  снимает мигратор; на живом проекте — руками, unica 0.13 их не принимает.

## Workflows (исполнение — кодом, не прозой)

- **`1c-e2e-author`** — агент сам пишет тест по бизнес-требованию: разведка →
  `tests/e2e/test_<name>.py` → прогон до зелёного → коммит → ЖР-сверка →
  вердикт.
- **`1c-e2e-run`** — прогон написанных тестов: pytest (модель не участвует) →
  при фейле расследование → независимая ЖР-сверка → вердикт.

Операции, подключение (launch/attach), e1cib-навигация и GUI-ловушки —
словарь `1c-testpilot` (интерфейсная карта; апстрим-дока TOOLS.md — полный
справочник операций).

## Грабли

- **Второй сеанс 1С на файловой базе навечно зависает** на «Загрузка
  конфигурационной информации» (0% CPU), пока базу держит первый клиент;
  оживает сразу после его гибели. Отсюда правило **GUI-тесты соло**: модуль
  GUI-тестов гасит 1c-db на время прогона и поднимает обратно (в пилоте —
  фикстура `solo_base`). Логика/API-тесты с поднятым 1c-db совмещаются
  свободно.
- Юзер профиля testpilot обязан существовать в ИБ: несуществующий — клиент
  молча висит на диалоге аутентификации и падает по wait.
- Не доверяй «выполнено» без readback: тест-клиент отвечает успехом, даже
  если форма не отрисовала.
- `desktop: isolated` обязателен на Linux — иначе клиент ловит фокус реальной
  сессии; требует пакета `xvfb` в системе.
- `find_object` требует ровно одно совпадение — уточняй условия поиска;
  после переподключения прежние объекты недействительны, получай `Element`
  заново.
- Долгие операции — ожидание с таймаутом (`tc_find wait` / повторный
  `find_object`), а не сон между шагами.
- Результат прерванного действия может быть неизвестен
  (`outcome_unknown`); `cleanup_pending=true` — обработчик ещё не отдал
  соединение, дождись `busy=false` перед переподключением.
- Окружение: `~/.local/venvs/1c-testpilot` (ставит `scripts/install_testpilot.sh`).
