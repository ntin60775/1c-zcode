# Unica: каналы, версии, переключение

Контур 1c-zcode — мягкая зависимость плагина Unica: без неё гейт исходников
отрезает единственный путь правки 1С. Формальная dependency-механика ZCode
не используется (нет version-ranges, живых примеров нет; переключение
каналов всё равно ручное). Проверка — `/1c-doctor`
(`UNICA_MIN = 0.15.0-rc.1`).

## Целевой канал: next, 0.15.0-rc.1 — переход 2026-10-26

Маркетплейс `IngvarConsulting/unica-marketplace`, ветка **next** (в реестре —
`unica-next`), плагин `unica@unica-next` версии `0.15.0-rc.1`, пин тега
`v0.15.0-rc.1` (коммит `ddf0aa7c7`). До переключения в UI на машине
остаётся `unica@unica 0.13.0`; после него старый канал — только для отката.
Держать обе установки одновременно **нельзя** — у обоих MCP-сервер имя
`unica`.

В пакете 0.15 есть `.zcode-plugin/plugin.json`, поэтому ZCode ставит юнику
нативно: отдельный Claude-обход не нужен. Порядок на каждой машине:

1. ZCode → Plugin Marketplace → Add → адрес
   `https://github.com/IngvarConsulting/unica-marketplace.git#next`.
   Появится каталог `unica-next`.
2. Удалить `unica@unica` (стабильную), установить `unica@unica-next`.
   Версия в карточке — `0.15.0-rc.1`.
3. Выдать exec-бит: распаковщик кэша ZCode теряет права на bootstrap.
   ```bash
   chmod +x ~/.zcode/cli/plugins/cache/unica-next/unica/*/bootstrap/bin/*/*
   ```
4. Начать новую задачу ZCode: старая сессия держит схему инструментов 0.13.
5. Проверить: `python3 .zcode/1c/scripts/unica_ping.py` и `/1c-doctor`.
   Доктор ждёт версию >= `0.15.0-rc.1`, ровно один канал и артефакты
   манифеста (в 0.15 — `v8-runner 0.15.3`).
6. После зелёной проверки снести старый кэш
   `~/.zcode/cli/plugins/cache/unica/unica/0.13.0` и
   `~/.zcode/cli/plugins/data/unica@unica`. Маркетплейс `unica` можно
   оставить для отката.

Если нужен конкретный кандидат, а не плавающая ветка, маркетплейс добавляют
по тегу: `…#v0.15.0-rc.1`. Плагин в нём тоже `unica@unica-next`, обновление
каталога оставляет версию.

## Откат на стабильную 0.13.0

1. Удалить `unica@unica-next`, установить `unica@unica` из ветки `main`.
2. Начать новую задачу.
3. Если контур уже требует `UNICA_MIN = 0.15.0-rc.1`, откатить и контур на
   тег `v0.4.62`: иначе доктор законно упадёт. Гейты при этом продолжают
   работать, но скиллы описывают поверхность 0.15.

Два канала одновременно = два MCP-сервера `unica`; это конфликт, а не
мягкое предупреждение. Живой демон прежней установки может держать бинарь
после удаления плагина — перед сносом кэшей проверить `ps`/`lsof`.

## Рантаймы и артефакты

Манифест установки (`runtime-manifest.json`, schema 2) для 0.15.0-rc.1:

| Артефакт | Версия | Примечание |
|---|---|---|
| `unica` | 0.15.0-rc.1 | ядро |
| `v8-runner` | 0.15.3 | был 0.14.0 — обновляется обязательно |
| `bsl-analyzer` | 0.2.86 | без изменений |
| `rlm-tools-bsl` | 1.42.0 | без изменений |

Кэш — `~/.zcode/cli/plugins/data/<id-плагина>/runtimes/<имя>/<версия>--<sha256>/<платформа>/`,
маркер завершённости — `.ready.json`. Резолв строгий по версии из манифеста;
недостающий артефакт всплывает `provider_unavailable` уже после живого
handshake. Диагноз и перенос из соседнего кэша — скилл
`1c-unica-artifacts`, проверка — `/1c-doctor`.

`unica_ping.py` берёт установку из `installed_plugins.json`, а не по `mtime`:
после смены канала на машине живут кэши обоих каналов. Handshake идёт
протоколом `2025-11-25` — 0.15 обслуживает `2025-06-18`, `2025-11-25` и
`2026-07-28`, более старую ревизию не предлагает.

## Поверхность 0.15: что изменилось

Имён по-прежнему 11: `view`, `apply`, `resolve`, `search`, `check`, `diff`,
`run`, `docs`, `task.get/result/cancel`.

- **Страницы.** `view`, `check`, `diff`, `docs`, `search` отдают длинные
  ответы страницами по `limit` (1–50) и `cursor`. Пока `cursor` непустой,
  ответ неполон. `check {}` без `at` отдаёт вердикт workspace и группы
  диагностик страницами; `check {at}` — находки узла.
- **Поиск.** Буквальный `search` без `role` идёт до последнего совпадения,
  первая страница несёт `data.totals` (точный объём). Роли только `symbol`
  и `semantic`; роли `lexical` нет. `symbol`/`semantic` могут остановиться
  после первого окна и пометить неполноту.
- **Пакетный `resolve`.** `resolve {paths: ["…:4", …]}` переводит много
  путей/строк в логические адреса одним вызовом; ошибка одного элемента не
  роняет остальные.
- **Длинное свойство.** `<узел>.Props.<имя>` читает свойство целиком, когда
  обычный `view` упирается в предел; `<узел>.Can.<op>` — контракт операции.
- **Новые операции `apply`.** `panels.set`, `homePage.set`, `attribute.copy`,
  `dimension.set`, `property.rename`, `props.set` на корне конфигурации и
  форме. Состав для узла — из `can`.
- **Словарь операций.** Поле `implemented` убрано; недоступной операции в
  словаре нет. Контракт вызова — `argsSchema` из `unica.run {}`; при
  `support.state: limited` допустимо только `support.supportedArgs`.
- **`unica.docs`.** Источники — `platform-help` и `development-standard`;
  `configuration-documentation` отвечает `unsupported_source` (#939).
  Длинная страница — страницами, ответ может прийти задачей
  (`status: working`): ждать `task.result`, принятие задачи не ответ.
- **Секреты и EOL.** Секрет подключения больше не попадает в сохранённые
  задания; правки XML не портят переводы строк в нетронутом тексте.

## v8project 0.15 и v8-runner

Полный справочник полей и регламент переезда —
`skills/1c-project-layout/references/v8project.md`. Коротко:

- `infobases` живут в `v8project.local.yaml`, поддерживается только `origin`.
  Основной файл с `infobases` ещё принимается, но 0.15 переносит базу в
  приватную копию `.build/unica/runner-project/`. Несколько именованных баз,
  верхнеуровневый `connection`, смесь `infobase` + `infobases` отвергаются.
- `builder`, `basePath`, `execution_timeout`, `push.partialLoadThreshold`
  отвергаются. Полная загрузка — `push full: true`.
- `build` — прежнее имя `push`; `infobase` — прежнее имя
  `infobases.origin`; принимаются один цикл.
- Исполнители `providers`: `designer`, `agent`, `ibcmd`, `ibcmd-rs`,
  `webinst`; прежние имена `build`/`dump`/`init`/`load`/
  `infobase.configuration.export` переименовываются в
  `push`/`pull`/`infobase.create`/`upload`/`download`.
- `upload`, `apply`, `reset` как операции `unica.run` недоступны (#1246).
  Загрузка `.cf`/`.cfe` — ibcmd, не раннер. `unica.apply` (MCP) — другое,
  он правит исходники.
- Файловая база принадлежит копии: запись из второй копии даёт
  `infobase_of_another_copy`. Каждой копии — своя база
  (`infobase.create`); владелец и проекция — скилл `1c-unica-worktree`.

## Известные границы 0.15

- **Публикации нет.** `unica.run` не публикует базу; `panels.set` и
  `homePage.set` — интерфейс, не веб-публикация. Контур закрывает это
  скиллом `1c-ibsrv-publish` через `publish_ib.sh`.
- **Дети HTTP-сервиса** (шаблоны URL, методы) по-прежнему не выражаются
  контрактом `object.create` целиком; апстрим — #529. Дети и права
  дописываются XML по разовой эскалации.
- **Размер вызова.** Необоснованный предел ~16 КиБ снят: #1309 закрыт,
  ресурсные лимиты сведены в реестр (#1312), отказ по размеру результата
  называет размер и предел. Нарезка большого модуля по границам процедур
  остаётся полезной для читаемости плана, но больше не обязательна.
- **`push` формы с ручным динсписком** падает `ConfigFilesError` (unica#1877);
  доставка — ibcmd, скилл `1c-ibcmd-delivery`.
- **Большие деревья.** 0.15 убирает отказы по размеру ответов страницами и
  снимками на диске; зонтик #1119 (нагрузка больших конфигураций) ещё
  открыт, admission-порог большого репозитория проверять живьём.
- **`extensions.list`/`pull`** — открытые #1797/#1798; серверной базе для
  IBCMD нужен `infobases.origin.dbms` (диагностика — #1103). Подсистемы
  основной конфигурации на файловой базе смотреть `execute_code` через 1c-db.

## Траблшутинг: «MCP process failed to start / Connection closed»

Причина (наблюдено 2026-10-01, повторяется после каждой переустановки):
распаковщик кэша ZCode не сохраняет exec-бит на
`bootstrap/bin/<target>/unica-bootstrap`, `launch.sh` падает с
«Permission denied». Лечение — разово на машину:

```bash
chmod +x ~/.zcode/cli/plugins/cache/unica*/*/*/bootstrap/bin/*/* \
  && python3 ~/.zcode/cli/plugins/cache/unica*/*/*/bootstrap/bin/linux-x64/unica-bootstrap --help 2>/dev/null
```

Затем перезапустить ZCode. Проверка без хоста — `unica_ping.py`: тот же
handshake (initialize → tools/list), версия сервера и глаголы; код 2 —
первый старт качает рантаймы, повторить позже.

Если сервер жив, но первый вызов провайдера отвечает
`provider_unavailable` — разошлись артефакты, не handshake: скилл
`1c-unica-artifacts`, `/1c-doctor` назовёт недостающий артефакт и версию.

## Работа в git-ворктри

Привязка воркспейса, второй экземпляр, cwd-механика хуков, владелец
файловой базы и проекция конфига — скилл `1c-unica-worktree`. Коротко:
воркспейс фиксируется при старте MCP, `cwd` вызова его не переключает;
хуки контура живут в `.zcode/config.json` абсолютными путями.

## История: линия 0.13

Стабильный 0.13.0 стоял с 2026-10-13 по 2026-10-26. Он содержательно равен
rc.7; инструменты того времени — `v8-runner 0.14.0`, `bsl-analyzer 0.2.86`,
`rlm-bsl 1.42.0`. Ключи, снятые ещё в rc.7 и остающиеся снятыми в 0.15:
`execution_timeout`, `push.partialLoadThreshold`; `builder` отвергался уже
тогда. Контракт `unica.run` с вложенными `args` и обязательным `dryRun`
действует с rc.5; асинхронные платформенные операции — с того же времени.
Кириллические имена source-set'ов принимаются с #1098; `extensions.list`
через previewed platform session работает (живая проба 2026-10-04); серверной
базе нужен `infobases.origin.dbms`.

Канал `unica-next` впервые подключали 2026-10-08 (rc.7), затем 2026-10-13
перешли на стабильный `unica`; 2026-10-26 вернулись на next уже за
0.15.0-rc.1. Оба канала одновременно не держать: конфликт имени MCP.
