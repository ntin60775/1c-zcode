# Unica: каналы, версии, переключение

Контур 1c-zcode — мягкая зависимость плагина Unica: без неё гейт исходников
отрезает единственный путь правки 1С. Формальная dependency-механика ZCode
не используется (нет version-ranges, живых примеров нет; переключение
каналов всё равно ручное). Проверка — `/1c-doctor` (`UNICA_MIN = 0.13.0`).

## Сейчас: канал unica (main-ветка маркетплейса), 0.13.0 — с 2026-10-13

Переключение с rc-канала исполнено 2026-10-13 (владелец в UI, хвосты —
агентом): маркетплейс `IngvarConsulting/unica-marketplace` ветка **main**
(в реестре — `unica`), плагин `unica@unica` 0.13.0 (пин тега `v0.13.0`,
кэш `~/.zcode/cli/plugins/cache/unica/unica/0.13.0/`). Канал `unica-next`
удалён из реестра и его манифест-кэш снесён. Апстрим на момент перехода
держал обе ветки маркетплейса на одном рефe `v0.13.0`; дельта контента
rc.7 → v0.13.0 — одна строка self-версии в `tools.lock`, инструменты
(v8-runner 0.14.0, bsl-analyzer 0.2.86, rlm-bsl 1.42.0) идентичны sha —
рантаймы из кэша переиспользуются, докачивается только unica-core.

Хвосты (после рестарта сессий, канон затирания): снести
`~/.zcode/cli/plugins/cache/unica-next/` и `~/.local/share/unica-next/`
(клон маркетплейса) — живые сессии до рестарта держат файлы старого кэша.

Историческая установка rc-канала (ветка `next`, была до 2026-10-13):

1. ZCode → Plugin Marketplace → Add → `IngvarConsulting/unica-marketplace`,
   канал/ветка **next** (в реестре появится маркетплейс `unica-next`).
2. Установить `unica` (получится `unica@unica-next`, версия вида
   `0.13.0-rc.N`, пин на иммутабельный тег).
3. Первый старт MCP скачает рантаймы (unica core, bsl-analyzer,
   rlm-tools-bsl, v8-runner) в plugin-data — соединение может жить
   несколько минут, `startup_timeout_sec: 900`.

## Переключение канала (механика на будущее)

Оба канала одновременно держать **нельзя** — у обоих MCP-сервер имя `unica`,
конфликт. Процедура:

1. Plugin Marketplace → Add → тот же репо, ветка **main**
   (появится маркетплейс `unica`).
2. Удалить `unica@unica-next`; установить `unica@unica` (стабильная 0.13.x).
3. Перезапустить сессию ZCode.
4. `/1c-doctor` — зелёный (версия ≥ 0.13.0, ровно один канал).

Что физически меняется: `installed_plugins.json` (id, маркетплейс, версия),
кэш `~/.zcode/cli/plugins/cache/unica/unica/<версия>/`; plugin-data нового
id (`…/data/unica@unica/`) при первом старте получает свои рантаймы —
общие инструменты (bsl-analyzer, v8-runner, rlm-tools-bsl) берутся из
кэша рантаймов по sha и не качаются заново. Старый кэш `unica-next` не
чистится автоматически — удалить руками после рестарта сессий.
Изменений в коде контура не требуется: сервер MCP у обоих каналов
называется `unica`, гейты матчат `mcp__unica__*`.

## Текущая версия: 0.13.0 (канал unica, с 2026-10-13)

До этого: 0.13.0-rc.7 (канал next, с 2026-10-08; переход на rc.7 —
[ишью #17](https://github.com/ntin60775/1c-zcode/issues/17)). Стабильный
v0.13.0 содержательно равен rc.7 (см. выше) — секции про breaking-ключи
ниже остаются каноном 0.13-линии.

**Breaking rc.7: v8-runner 0.14 отвергает ключи v8project.yaml**
(`invalid_source`, «remove the key»):

- `execution_timeout` — общего дедлайна команды больше нет, только per-step;
- `push.partialLoadThreshold` (и legacy `build.partialLoadThreshold`) —
  порога частичной загрузки нет: push без `full: true` частичный и так;
- словарь ops на пустой `run {op: ""}` больше не отдаётся
  (`unsupported_operation`), canonical-имя параметра полной загрузки —
  `fullRebuild` (алиас `full` принимается, контурные `rebuild_rules` живы).

Шаблон `v8project.template.yaml` (навык 1c-project-layout) этих ключей не
ставит с v0.4.41; в живых проектах ключи убраны 2026-10-08.

Прочее rc.7 (release notes): фиксы форм (ID элементов, HTMLDocumentField),
meta (Form.bin, константы через props.set, ScheduledJob defaults), launch
без sources, EOL-стриминг в check, сняты произвольные квоты рантайма/
поиска, saved plans переживают вызовы.

Контракт `unica.run` rc.5 (не помечен breaking, но ломает плоскую форму):

- аргументы операции — **вложенно**: `{op: "push", args: {sourceSet: ...},
  dryRun: true|false}`; плоская `{op, sourceSet}` → «canonical invocation
  has unknown argument»;
- `dryRun: true|false` обязателен явно (включая read-only `extensions.list`);
- платформенные операции (`push`, `extensions.list`, …) — async: ответ =
  задача, результат `unica.task.result {taskId, waitMs: 0..7000}`.

Проверено живьём (2026-10-04): **кириллические имена source-set'ов
принимаются** (фикс #1098; наш #1127 закрыт с repro — ошибки для
«Тесты» и латинского контрольного идентичны, «not declared», до самой
поисковой проверки); `extensions.list` работает через previewed platform
session (раньше ibcmd exit 255 — #1103); adapter `v8-runner/0.11.3`.

## Траблшутинг: «The MCP process failed to start / Connection closed»

Симптом: в Settings → MCP у сервера `unica` красная точка, «process failed
to start»; кнопка обновления плагина не помогает.

Причина (наблюдено 2026-10-01): распаковчик кэша плагинов ZCode **не
сохраняет exec-бит** — `bootstrap/bin/<target>/unica-bootstrap` лежит с
правами `rw-rw-r--`, `launch.sh` падает на `exec` с «Permission denied».
Появляется после каждой (пере)установки/обновления плагина юники — кэш
пересоздаётся.

Лечение (разово на машину, до фикса распаковщика):

```bash
chmod +x ~/.zcode/cli/plugins/cache/unica*/*/*/bootstrap/bin/*/* \
  && python3 ~/.zcode/cli/plugins/cache/unica*/*/*/bootstrap/bin/linux-x64/unica-bootstrap --help 2>/dev/null; \
  echo 'затем перезапусти ZCode (или пере-включи плагин unica)'
```

Проверка без хоста: `python3 .zcode/1c/scripts/unica_ping.py` — делает тот
же handshake, что хост (initialize → tools/list), печатает версию сервера и
глаголы; встроена в `/1c-doctor` (код 2 = первый старт качает рантаймы —
повторить позже). Если после chmod сервер жив, но тормозит первый вызов —
это докачиваются остальные артефакты манифеста (bsl-analyzer, v8-runner),
`startup_timeout_sec: 900` даёт им время. Если закачка на машине
невозможна (github releases недоступен), артефакт так и не появится, а
провайдер будет отвечать `provider_unavailable` — диагноз и перенос из
соседнего кэша установки в скилле `1c-unica-artifacts`; `/1c-doctor`
сверяет манифест с кэшем.

## Поставка и работа над конфигурацией: границы с ibcmd

Решение владельца (2026-10-20): выгрузка/загрузка исходников и поставка —
напрямую `ibcmd` (скилл `1c-ibcmd-delivery`: цикл поставки, цепочка
заимствований, adopted-канон, нормализованная сверка); работа над
конфигурацией — unica. Выгрузка не равна авторской правке: инвариант
«исходники правятся только через unica.apply» про авторскую работу, гейты
доставку ibcmd не блокируют (проверено живым `export --sync` — ноль диффов).

**Режим «unica недоступна»** (наблюдение 2026-10-20; свойство юники, не
платформы): на больших деревьях git-инспекция admission сваливается за
порогом классифицируемых ресурсов («resource classification count exceeds
65536», наблюдалось при 128k файлов; `readinessState=incomplete`) — отказывают
apply и view («source set was not admitted by the workspace actor»), чтение
при этом может продолжать работать. Схема source-set'ов при этом валидна —
отказ не про запись набора. Порядок действий: поставка живёт на ibcmd и от
unica не зависит; правки исходников — через allowlist эскалаций (скилл
`1c-contour`); рестарт MCP-сессии как первая диагностика — гипотеза (в
исходном ране не проверена), проверить при первом живом столкновении и
дописать сюда; при случае — вопрос апстриму рядом с #1797/#1798.

**Рабочий source сверки**: на стендах с частично настроенными провайдерами
(например platform-syntax-help недоступен — «установка платформы не разрешена»)
сверку doc-gate закрывает `unica.docs {source: development-standard}` (живой
v8std). Хук с v0.4.54 считает осмысленным ответ с живыми секциями —
недоступные провайдеры сверку не роняют.

**Известный gap push**: `unica.run push` набора с формой с ручным динсписком
падает «ConfigFilesError» (дважды, в том числе на пустой копии ИБ; причина не
установлена — апстрим unica#1877). Доставка таких форм — ibcmd; детали —
скилл `1c-ibcmd-delivery`.

## Замечания

- RC-обновления внутри next (`0.13.0-rc.3` → `rc.4`) — обычный Update
  плагина; doctor предупредит, если версия ушла ниже минимума.
- Артефакты рантайма (bsl-analyzer, v8-runner, rlm-tools-bsl, unica)
  резолвятся строго по версии из `runtime-manifest.json` плагина: после
  обновления плагина кэш может остаться на прежних версиях, а неудавшаяся
  закачка оставляет `.partial` — провайдеры отвечают
  `provider_unavailable` при живом сервере (ping этот провал не видит).
  Диагноз и перенос из соседнего кэша установки — скилл
  `1c-unica-artifacts` (вендорится в проекты); `/1c-doctor` сверяет
  манифест с кэшем.
- Рантаймы старого omp-контура (`~/.codex/unica/runtimes/0.12.3`) не
  конфликтуют с ZCode-каналом (другой каталог), удаляются только при
  финальной чистке omp (см. MIGRATION-FROM-OMP.md).
- Работа в git-ворктри, второй экземпляр сервера и cwd-механика хуков —
  скилл `1c-unica-worktree` (вендорится в проекты с контуром).
- Дети HTTP-сервиса (шаблоны URL, методы) 0.13 не выражает: `object.create`
  ставит только корневой объект, коллекций детей и `method.add` в
  canonical-реестре нет — дети и права `Use` ролям дописываются правкой XML
  по разовой эскалации. Апстрим — ишью `IngvarConsulting/unica` #529
  (подтверждено на rc.7 живым раном, 2026-10-09; права на детей —
  в комменте там же).
- Полезная нагрузка вызова unica ограничена ~16 КБ: 12 000 байт проходит,
  16 000 отвергается `invalid_request`, лимит в ошибке не назван (ишью
  #1309). Большой модуль резать по границам процедур (после каждой вставки
  текст остаётся синтаксически полным), каждый кусок валидировать
  `unica.check`, итог сверять байт-в-байт.
- Первый `push --full` в свежую копию ИБ падает «no memory of the
  infobase» — нужен `--force` (v8-runner 0.14: у раннера нет памяти об этой
  базе). Выгрузка `.cfe` — `download --extension`.
- Синтакс-валидация юники и push не ловят необъявленную переменную (модули
  компилируются лениво) — валидация кусков при заливке не гарантирует
  компилируемость; финальный контроль — ревью или компиляция.

## Нативная ZCode-поддержка в Unica (PR #1097, Draft — следить)

`IngvarConsulting/unica` #1097 добавляет ZCode третьим хостом общего пакета:
один каталог плагина получает `.zcode-plugin/plugin.json` рядом с
`.claude-plugin/`, скиллы и `.mcp.json` общие, отдельного сервера/launcher'а
для ZCode нет. Для контура это значит:

- **Процедура переключения выше не меняется** — при выходе релиза с этим PR
  канал `unica` (main) будет обслуживать ZCode нативно; используем ту же
  схему «снять next → поставить unica».
- **Правило одного включённого экземпляра** остаётся, но мягче: достаточно
  отключить старую установку в Settings → Plugins (кэш удалять не нужно —
  данные в plugin-data переживают обновления). Две включённые = два
  MCP-сервера `unica`, конфликт.
- **Кэш рантаймов**: приоритет `UNICA_RUNTIME_CACHE_DIR` →
  `CLAUDE_PLUGIN_DATA/runtimes` → `ZCODE_PLUGIN_DATA/runtimes` → CODEX-пути.
  ZCode подставляет совместимые `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA`,
  поэтому смена хост-манифеста на расположение плагина и рантаймов не
  влияет. Конфликт `ZCODE_PROJECT_DIR` ≠ `CLAUDE_PROJECT_DIR` даёт отказ
  юники — держать в голове при вложенных воркспейсах.
- **Схему проверять в НОВОЙ задаче**: старая сессия может держать
  устаревшую схему 0.12 (`unica.runtime.execute`) — наш доктор и стендовые
  проверки это уже требуют, совпадает.
- Открытые проблемы PR, релевантные нам: `check.cursor` под OpenAI-хостом
  ломается нормализацией `required:[]` (вынесено в PR #1120 — апдейтить при
  релизе); SIGABRT v8-runner при full push на 1С 8.5.1 (issue #1111; целевая
  платформа пилота 8.3.27.2214 — не воспроизводится, но помнить для
  будущих проектов на 8.5).
