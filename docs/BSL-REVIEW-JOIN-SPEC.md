# Спека: скрипт-джойн ревьюера стандартов (`bsl_review_join.py`)

Ишью #24, раздел «Эволюция» — единственный этап ревьюера, оставшийся без
реализации. Всё прочее вендорено и выпущено в v0.4.48 (918479a → 246a149).
Условие этапа «формат вывода `unica.check` стабилизируется» исполнено:
уника 0.15.0-rc.1 (канал next с 2026-10-26) отдаёт `check` страницами с
`cursor`; контракт ядра (`status`, `diagnostics[]`) не изменился.

Статус: спека. Реализация не начата. Спеку утверждает владелец; готовый
скрипт принимает владелец.

## 1. Цель

Детерминированная склейка трёх входов — сохранённый вывод `unica.check` ×
`references/routing.md` × `.zcode/1c/standards-exceptions.yaml` — в
размеченный перечень находок и готовые строки отчёта. Скрипт забирает
рутину гашения и группировки, агент остаётся там, где нужны факты:
метаданные (`unica.view`), раскрытие стандарта (`unica.docs`), сверка шума.

## 2. Не-цели

- Не вызывает MCP и сеть вообще — чистая функция над файлами, stdin/stdout.
- Не применяет домен A (стайл-пак): находки пака через таблицу не идут,
  их вердикт `fix` со основанием «файл пака» — как и сейчас, агентом.
- Не решает конфликт доменов и не проверяет метаданные: `compile-risk`
  остаётся за агентом (шаг 6 SKILL.md).
- Не пишет журнал исключений и не предлагает правки кода.
- Не хук: enforcement ревьюера — протокол agents-section, без хука
  (решение владельца от 2026-10-11 не пересматривается).

## 3. Входные контракты

### 3.1 Вывод `unica.check` (0.15.0-rc.1)

Вход — один или несколько JSON-файлов, каждый содержит structured content
ответа `unica.check` для одного узла (все страницы пагинации узла: ответ
отдаётся страницами по `limit` ≤ 50 с `cursor`). Обязательное ядро
структуры: `status` (`passed`|`failed`) и `diagnostics[]`; каждая находка
несёт как минимум код и сообщение (док скилла code-diagnostics: «код,
важность, место и стандарт»). `validators` — при наличии; отсутствие даёт
предупреждение, не облом: живой readiness-ответ юники validators не отдаёт.
Точные имена полей места/важности фиксируются снапшот-фикстурой живого
ответа — спека их не угадывает (см. §9, шаг 1). Скрипт обязан:

- отделять обёртку от ядра и валидировать ядро; незнакомая схема —
  fail-closed, код возврата 2 с точным сообщением, какого поля не хватило;
- не путать «пустой `diagnostics` при `status: passed`» (доказательство
  чистоты) с отказом провайдера: отказ приходит как ошибка вызова, до
  скрипта — на входе его не бывает;
- подсчитывать `suppressed` базовой линии, если поле присутствует
  (`known`/`new`), и переносить счётчики в отчёт — видимость сохраняется;
- признак недочитанных страниц: в последней поданной странице остался
  непустой `cursor` — находки размечаются, отчёт помечает
  `pages_complete: false`; вердикты при этом не подделываются —
  «страницы не дочитаны» уходит агенту строкой, требование полноты
  скрипт выдумывать не вправе (проверить сам он её не может).

### 3.2 `references/routing.md`

Единственный источник данных о маршруте — md-таблица; машиночитаемого
дубликата нет и не появится (см. §8, развилка 2). Парсер строгий:
pipe-таблица с заголовком «Код диагностики | Класс | Действие по
умолчанию | Стандарт | Блокер»; нарушение формы — fail-closed, код 2.

Матчится только та строка, у которой ячейка «Код» — точный код диагностики,
опционально с маркером-уточнением в скобках: `DeprecatedPlatformApi`
или `DeprecatedPlatformApi (ТекущаяДата → ТекущаяДатаСеанса)`. Правила:

- код сопоставляется находке точно, регистр значим;
- маркер — подстрока сообщения находки (уточняет маршрут у одного кода);
  строка без маркера — fallback после всех строк с маркерами;
- строка-семья («Диагностики именования…», «Подсказка „используйте X.Y“…»)
  и строка «Неизвестный код» скриптом не матчится — их применяет агент,
  как и сейчас; для находки без матча скрипт ставит `matched: false`,
  агент ведёт её по таблице руками.

### 3.3 `.zcode/1c/standards-exceptions.yaml`

Формат — references/exceptions-contract.md, `version: 1`. Python
ограничен stdlib (канон контура), PyYAML не вводится (см. §8, развилка 3),
поэтому парсится узкое подмножество формата: скаляры, список `exceptions`,
блочный скаляр `rationale`. Правила:

- `version` отлична от 1 — fail-closed, код 2 («незнакомая версия формата,
  сверку исключений остановил»);
- структурный облом (нет `exceptions`, элемент не отображение) — код 2;
- неизвестный ключ записи — предупреждение в отчёт, сверка продолжается;
- запись без непустых `rationale` и `owner` — недействительна: не гасит
  находку и попадает в `journal_problems` (контракт прямо требует
  трактовать её как отсутствие исключения и сообщать);
- отсутствие файла легально — сверка исключений пропускается целиком.

Совпадение находки с записью: `diagnostic` точно + `subject` — подстрока
сообщения находки + `scope` покрывает узел (`all`; `node:<адрес>` равен
адресу вызова; `file:<путь>` — если путь различим в находке, иначе запись
не применяется и это фиксируется в `journal_problems`, молча не гасить).
Класс `compile-risk` и вердикт `risk` журналом не гасятся никогда.

## 4. Выход

`--json` (по умолчанию): один JSON-объект в stdout, `schema:
"bsl-review-join/1"`; ошибки — только в stderr. Поля:

- `node`, `pages`, `pages_complete`, `suppressed_known`, `suppressed_new`;
- `counts` — total / live / waived / report / unknown / escalated;
- `findings[]` — на каждую диагностику: `code`, `message`, место,
  `row` (класс, действие по умолчанию, стандарт, блокер — из строки
  таблицы), `verdict_candidate`, `exception` (id записи, если гашено),
  `report_line`;
- `journal_problems[]`, `warnings[]`.

`verdict_candidate` выводится из класса строки:

| Класс | `verdict_candidate` |
|---|---|
| `deprecated-api`, `naming` | `fix` |
| `compile-risk` | `risk` (`exception` всегда null) |
| `metadata` | `fix` + `escalated: true` — правка кода не лечит |
| `query-performance`, `metric` | `report` |
| `form` | `fix` + `route: domain-A` |
| `analyzer-noise` | `verify-noise` (агент сверяет с эталоном) |
| без матча | `needs-docs` (агентский шаг 4/6) |

`report_line` — «источник → требование → вердикт → основание» в форме
шага 8 SKILL.md; для `waived` — одна строка с id записи и основанием.
Видимость гашеных находок не теряется — это контракт журнала.

`--text` — те же `report_line` плюс сводка и предупреждения, для вставки
в чат.

## 5. CLI

```
python3 bsl_review_join.py --node <addr> --check-out FILE [--check-out FILE…] \
                           --project ROOT [--routing PATH] [--exceptions PATH] \
                           [--json|--text]
```

Один вызов — один узел (процедура поузловая; `check {}` в 0.15 даёт только
вердикт workspace и группы диагностик, не полный поток находок); страницы
одного узла — повторением `--check-out`.
По умолчанию routing берётся относительно скрипта
(`../skills/1c-bsl-review-standards/references/routing.md` — mapping
`scripts/ → .zcode/1c/scripts/` и скилла уже есть в deploy.json, новых
mappings не нужно), exceptions — `<project>/.zcode/1c/standards-exceptions.yaml`.
Коды возврата: `0` — прогон отработал (есть находки или чисто — решает
агент по JSON), `2` — fail-closed по любому из входов.

## 6. Алгоритм

1. Прочитать страницы, валидировать ядро (§3.1), дедуп по (код, место).
2. Смонтировать `diagnostics[]` в порядке страниц, посчитать suppressed.
3. Для каждой находки: маршрут по таблице (§3.2) → кандидат-вердикт (§4).
4. Гашение журналом до раскрытия (§3.3): совпало и класс не `compile-risk`
   → `waived`, `exception` = id; иначе живая.
5. Сборка `findings[]`, счётчиков, `report_line`, проблем и предупреждений.

## 7. Тесты

`tests/test_bsl_review_join.py`, канон контура — скрипт как процесс,
stdin/argv → код возврата и stdout. Фикстуры в
`tests/fixtures/bsl-review-join/`. Случаи:

- снапшот живого ответа `unica.check` с находками — матч по коду, выбор
  строки с маркером перед fallback-строкой;
- `waived` гасит находку, строка отчёта сохраняется; `waived` не гасит
  `compile-risk`;
- запись без `rationale`/`owner` не гасит и попадает в `journal_problems`;
- `version: 2` — код 2, частичного отчёта нет; файл отсутствует — легально;
- недочитанный `cursor` — `pages_complete: false` и строка-предупреждение;
- находка без строки таблицы — `needs-docs`, не облом;
- незнакомая структура диагностики — код 2 с указанием поля;
- демо-таблица с нарушением заголовка — код 2.

Снапшот живого ответа — единственная внешняя зависимость: снимается в
живом проекте при первой пробе; до него юнит-тесты идут на минимальной
заглушке по форме из дока (`code`/`message`), при живом прогоне заглушка
заменяется снапшотом, а не расширяется на глазок.

## 8. Развилки — выбор и отвергнутое

1. **Скрипт вызывает MCP сам vs принимает сохранённые ответы.** Выбор:
   принимает. Чистая функция тестируется процессами без сети и даёт
   одинаковый отчёт на одинаковых входах; скрипт-обёртка MCP недетерминированна
   и вне юнит-канона контура.
2. **Парсить `routing.md` vs завести `routing.json`-дубликат.** Выбор:
   парсить md. Данные живут в одном месте — рассинхрон двух копий
   исключён по построению (грабля «обновления затирают старое» в обратную
   сторону: вторая копия молча устаревает). Строгий парсер + тест на
   вендорен-таблицу держат форму под контролем.
3. **YAML: узкий stdlib-парсер vs PyYAML vs перевод журнала в JSON.**
   Выбор: узкий парсер подмножества контракта. PyYAML — зависимость вне
   stdlib, JSON — ломает уже вендорен-контракт и журнал, который владелец
   ведёт руками. Fail-closed на `version` прикрывает риск кривого парсинга
   незнакомого синтаксиса.
4. **Пагинация: требовать дочитанный обход vs помечать неполноту.**
   Выбор: помечать. Скрипт не может отличить «курсор остался потому, что
   есть ещё» от «остался пустой», а блокировать ревью выдуманным
   требованием — ложный облом; полноту держит процедура агента.

## 9. Порядок реализации и приёмка

1. Снапшот живого `unica.check` в узле с находками (сессия живого
   проекта — по команде владельца).
2. Парсеры routing и exceptions, ядро склейки, CLI (`scripts/bsl_review_join.py`).
3. Тесты §7; прогон всего набора `tests/test_*.py`.
4. Дельта поставки: SKILL.md — шаги 4–5 дополняются вызовом джойна
   (формулировка «ускоряет, отсутствие скрипта процедуру не ломает»);
   routing.md — сноска о формате ячейки «Код» (код или код с маркером в
   скобках, матчинг маркера подстрокой сообщения); exceptions-contract.md —
   сноска о машинной обработке scope (`file:` применяется только при
   различимом пути); README — состав scripts/.
5. Проверки контура: forbidden-names, `lint_skill_frontmatter.py`
   (frontmatter скиллов не меняется, но прогон обязателен), полный тестовый
   набор.
6. Релиз — по команде владельца; живая проба ревьюера с джойном — при
   раскатке (ишью #25), приёмка — владелец.
